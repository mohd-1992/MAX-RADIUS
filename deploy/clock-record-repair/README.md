# اختبار تصحيح سجلات حادثة الساعة — محلي فقط

هذا مرشح مختبري لتصحيح **التواريخ فقط**. لا يحمل اعتمادًا ولا يتصل بالعميل، ويرفض اسم قاعدة لا يبدأ بـ`max_clock_repair_lab_`. لا يتضمن مشغل تطبيق حي أو ترحيلًا عند بدء النظام. وقاية الإقلاع في [clock-guard](../clock-guard/README.md) مهمة منفصلة مؤجلة.

## المرشح المعدل: أولوية المرور الفعلي

[priority_repair.py](priority_repair.py) يضيف READ COMMITTED لاتصال التصحيح المخصص فقط؛ لا يغير العزل العام أو اتصالات RADIUS، ولا يضيف فهرسًا أو يعدل التريغر. بذلك لا تبقى أقفال الفراغات والصفوف غير المطابقة من مسح الحجوزات محتجزة كما في المرشح القديم. تكلفة المسح نفسها لا تختفي.

كل كرت معاملة مستقلة وإيصال مستقل، وأقفال المفاتيح المحددة تستعمل NOWAIT. الحساب المشغول يؤجل التصحيح بدل انتظار الكاتب. حد العبارة50ms وحد المعاملة250ms، مع مراجعة من يحجبه اتصال التصحيح وأولوية للطلب المنتظر، ثم توقف بعد أول تعارض دون إعادة محاولة تلقائية. بين المعاملات مهلة20ms خارج الأقفال لتخفيف العمل. هذه الحدود ليست ضمانًا لحد أعلى مطلق لزمن خدمة حي تحت تعطل الشبكة أو التخزين.

التنفيذ الجزئي صريح وقابل للاستئناف من إيصالات الكروت المكتملة، دون طرح مزدوج أو تراجع تلقائي فوق استعمال أحدث. يبقى السجل المتعارض دون تغيير، والتراجع لكل كرت مشروط بعدم وجود محاسبة/قبول/بيع/عقد أحدث. لا يحتفظ هذا المرشح بقفل غياب reservation ضد كاتب إداري يتجاوز مسارات النظام؛ مسار INSERT الطبيعي يربط الحجز بمعرف صف المحاسبة الجديد فقط، وليس صفًا تاريخيًا مغلقًا. يعاد فحص حواجز المستهدف قبل الكتابة، ويجب التحقق من ثبات مسارات الكاتب وتعريفات SQL عند إعداد أي تطبيق حي.

**لا وعد بانعدام تأخير مطلق:** كاتب يصل إلى الكرت نفسه بعد أخذ القفل قد ينتظر زمنًا قصيرًا حتى التراجع أو commit. رصد الانتظار ومهلات التصحيح يقللان الأثر، ولا يثبتان صفر أثر في الإنتاج. النسخة القديمة أدناه محفوظة للمقارنة؛ وجود هذا التحسين لا يعني تطبيقه على العميل.

يشغّل `CLOCK_REPAIR_MODE=priority` الفحوص الجديدة. [حالات التزامن](../../tests/clock_record_priority_cases.py) تستعمل دوال الحجز وسياسة أول استعمال الفعلية في قاعدة مؤقتة، و[fixture UDP](../../tests/clock_record_udp_fixture.py) يشغل FreeRADIUS وشيفرة SQL المحفوظة في شبكة Docker داخلية بلا منافذ UDP منشورة على المضيف. مدخل Docker الأصلي لا يشغّل، ولا يضاف مسار أو NAT. ترخيص SQL fixture محدود ومستقل، وليس توقيع ترخيص عميل أو اختبار issuer. ردود UDP تتحقق بتوقيع الاستجابة، ثم تقارن جلسات DB وStop والعدادات؛ لا ACK وحده. هذا ليس اختبار RouterOS حقيقيًا أو نسخة كاملة من بيئة العميل.

## المشغّل المقيد بالعميل — 17 أكتوبر2026

أجاز المستخدم تجهيز مشغّل التنفيذ والتراجع واختباره محليًا وفحص كل الجلسات قراءة فقط، ثم التطبيق عند نجاح الاختبارات. نجحت63حالة معزولة، منها مسارا watchdog بالتراجع قبل الاعتماد وبقاء التصحيح بعده، وتطبيق50كرتًا والتراجع من الإيصالات المخزنة فيDB، ورفض التكرار أو البيع/المحاسبة الأحدث. تضمنت52استجابةUDPموقعة، دون اختبار صناعي على العميل. لا يمنح هذا المستند إذنًا لأي تشغيل لاحق أو بيئة أخرى.

[customer_operator.py](customer_operator.py) يربط العملية بالمضيف والحاويات وقاعدة البيانات والتريغرات ودوال المصادقة ومعرفات50جلسة/57مصادقة المحددة. [plan_codec.py](plan_codec.py) يحفظ الأنواع فيJSONمنضبط، مع تجزئة كلمات المرور في الإيصالات. [operator_kernel.py](operator_kernel.py) يتلقى الاعتماد فيstdinبالذاكرة فقط ولا يستورد التطبيق. [host_dispatch.py](host_dispatch.py) يتحقق من الحزمة والنسخة المشفرة المتحقق منها خارج المضيف، ويمنع تكرار خطوات التنفيذ ويفصل التجربة والاعتماد والبقية. التشغيل الافتراضيstatus، وقفل المضيف يمنع تداخل التنفيذ والمراقب. التراجع من سجلDBنفسه، لا من استعادة قاعدة قديمة.

يُنشأ جدول استرداد مستقل واحد لا يرتبط بجداول التطبيق، دونALTERأو تعديل تريغر/فهرس. تبقى المعاملات منفصلة لكل كرت، بميزانية250msومهلة عبارة50msوقفلNOWAIT، وإعدادات الجلسة مخصصة لاتصال التصحيح وحده. فشل الشرط يوقف البقية دون إعادة تلقائية؛ قد يكتمل جزء فقط ويُوثق. المشغل يُحمل في ذاكرة الحاوية المثبتة؛ لا نشر صورة ولا تغيير/appولا إعادة تشغيل خدمة. أدلة التطبيق الفعلية ونتيجته في سجل التسليم الخاص، ولا يستدل من نجاح المختبر وحده على تنفيذ حي أو صفر أثر.

## المرشح السابق ونطاق الدليل المحفوظ

## نطاق الدليل

قراءات العميل المحمية حصرت 50 صف محاسبة مغلقًا و57 سجل مصادقة في نافذة الساعة المتقدمة؛ 7 سجلات مصادقة تخص فحص Core الداخلي ولا تمثل بطاقات إضافية. سجل journal من الإقلاع نفسه أثبت قفزة ساعة مقدارها `-10743.186176` ثانية، ومصدر SQL الفعلي يبني الوقت من ساعة استقبال المضيف مع طرح Acct-Delay-Time.

الأعمدة الفعلية للمحاسبة DATETIME(0)، وauthdate هو TIMESTAMP(0). المرشح يستعمل إزاحة **-10743 ثانية** مع جلسة SQL صريحة `+03:00`، ويحافظ على فروق الأوقات ودقة التخزين. فرق التقريب 0.186176 ثانية ليس ضمانًا لدقة الزمن الحقيقي؛ التوقيت الناتج **محسوب من قفزة الساعة** وليس وقت حزمة NAS مستقلة مسترجعة. تحفظ الأصول والدليل في الإيصال الخاص. لا يُطرح ثلاث ساعات عشوائيًا ولا يعاد تكوين الوقت من مدة الجلسة.

## حدود التغيير

يسمح فقط بتواريخ start/update/stop في المعرفات المغلقة المجمدة، وauthdate في معرفات المصادقة المحددة. يحفظ كل الأعمدة الأخرى، بما فيها acctuniqueid والهوية والعدادات والثواني وسبب الإغلاق والاعتماد. لا تغيير للحالة أو الحصة أو الإضافة أو الدورة أو تاريخ انتهاء البطاقة أو المبيعات أو baselines أو الترخيص. لا حذف أو إعادة تفعيل أو اصطناع Stop أو توليد طلبات للراوتر.

يرفض الصف المفقود أو المتغير أو المفتوح أو الخارج عن النافذة أو الذي يعبر حد الدورة بعد التصحيح. يقارن تعريفَي تريغر التحديث الفعليين دون تعطيلهما، ويرفض seal أو reservation للمستهدف. العملية معاملة واحدة مع تحقق قبل commit وإيصال قبل/بعد قابل للاشتقاق من الأصول والإزاحة. التكرار لا يطرح الإزاحة مرتين؛ لا إعادة apply بعد التراجع. التراجع يرفض المحاسبة أو القبول أو baseline أو البيع الأحدث للحساب أو تغير البطاقة، ولا يستعيد قاعدة قديمة فوق الاستخدام الجديد.

الأقفال محدودة بمهلة ثانيتين. اختبار التزامن أثبت انتظار كاتب الصف/العقد نفسه حتى انتهاء المهلة. **المرشح غير معتمد للتطبيق الحي**: قراءة information_schema وEXPLAIN فقط أكدت غياب فهرس يبدأ بـradacctid في حجوزات العميل وخطة مسح ALL، دون تنفيذ SELECT القفل. الاختبار39 أعاد إنتاج انتظار حجز دخول لحساب مختلف حتى مهلة1205 عند إبقاء المعاملة مفتوحة عمدًا. هذه مهلة fixture، وليست تأخيرًا مقاسًا على العميل، لكنها تمنع الاستدلال من حفظ البيانات إلى انعدام أثر الخدمة. يلزم تضييق الأقفال واختبار المصادقة/الحجوزات المتزامنة قبل اعتماد مشغل حي؛ لا تعطيل تريغر ولا إضافة فهرس على العميل في هذه الجولة.

## تشغيل الفحص المعزول

المشغل [run_clock_record_repair_lab.py](../../tests/run_clock_record_repair_lab.py) يتطلب مساري `CLOCK_REPAIR_REPORT_DIR` (جديد) و`CLOCK_REPAIR_EVIDENCE_DIR` (أدلة SELECT الخاصة). ينشئ MariaDB جديدة باسم ومعرف مستقلين ومنفذ loopback عشوائي؛ يستعمل مخطط المصدر دون حسابات bootstrap. يسقط الهوية الأصلية ويولد أسماء وعناوين وجلسات مختبرية؛ يستعمل فقط الأوقات والأرقام اللازمة لاختبار الحساسية. لا ينسخ قاعدة العميل كاملة ولا يشغل initializer أو التطبيق أو NAS.

التريغران الفعليان للتحديث يستخرجان من الدليل الخاص. تقارن اختبارات أعمدة الجداول الأربعة النوع والترميز ودقة التاريخ مع metadata العميل. هذا ليس اختبارًا لبقية تريغرات INSERT أو بروتوكول NAS أو جميع بيانات الإنتاج. تبقى ملفات الاعتماد والتشخيص والإيصالات خارج Git والصور، وتحتفظ الحاوية الجديدة متوقفة.

النتيجة: 38 حالة سلامة/تراجع ناجحة، واختبار إضافي ناجح في **إعادة إنتاج القيد المعروف** أعلاه. نجاح39حالة لا يعني اعتماد الإصلاح الحي. المصدر المفهرس محليًا في [SOURCE_MANIFEST](SOURCE_MANIFEST.json)؛ لا بيانات أو اعتماد في الفهرس.

قبل أي تطبيق حي مستقل: يعرض التقرير للمستخدم، وتراجع الأدلة والهوية والصفوف والعقود وخطة الأقفال مجددًا، وتتحقق نسخة مشفرة حديثة خارج المضيف وخطة تنفيذ وتراجع مناسبة. لا يمنح هذا الملف أو نجاح المختبر تفويض كتابة حية.
