# نشر إصلاح الاستعادة ضمن 2.6.9 وربط الإنشاءات الجديدة

اكتمل في **1 نوفمبر 2026** بتفويض المستخدم: تعديل Web ورفعها بوسم مستقل، ثم جعل المنظومات الجديدة في `control.max-r.cc` تختار الصورة المصححة. لا تحديث لمنظومة قائمة، ولا إعلان تحديثات أو تغيير `latest`، ولا تغيير Core أو محركات قواعد البيانات.

تحققت مطابقة Registry للصورة المختبرة وطبقاتها وإعداد تشغيلها. توقيع runtime صالح ومفتاح الناشر ثابت، و**216 ملف runtime سابقًا دون تغيير**. الاختلاف: وحدة `backup_service` المعدلة وإضافة وحدة `mysql_restore_stream`. طبقات الأصل وإعدادات التشغيل محفوظة؛ بقي Web/Core `latest` كما كانا قبل الرفع.

## الإصلاح ونطاق المصدر

- يجهز SQL كاملًا في ملف مؤقت محدود الذاكرة قبل بدء عميل MariaDB. يعيد ربط `DEFINER` في تعريفات العروض والدوال والمشغلات والإجراءات والأحداث بحساب الوجهة `CURRENT_USER`، ويحافظ على `SQL SECURITY` والبيانات والنصوص والتعليقات وصيغة `DELIMITER`.
- يعالج التعليقات التنفيذية الخاصة بـMySQL/MariaDB والاقتباس والـBOM. المسار السريع لعبارات INSERT يتحقق من الاقتباس ونهاية العبارة قبل نسخها؛ لا يتجاوز تعريفًا آخر في السطر نفسه.
- يرفض الاقتباس أو التعريف المبتور قبل بدء عميل الاستيراد. الحد الحالي 2GiB لنص SQL و16MiB للسطر/الرمز المخزن؛ لا دعم معلن لتصدير يغير الوضع إلى `NO_BACKSLASH_ESCAPES`، بل يرفضه بوضوح قبل الاستيراد.
- يحفظ جميع صفوف ترخيص الوجهة ويعيدها بمعاملة، بما فيها الحالة والحدود والنص الأصلي للحزمة، دون استخدام ترخيص النسخة المنقولة. يعمل ذلك في النجاح ومسار فشل الاستيراد؛ الوجهة غير المرخصة لا ترث ترخيص المصدر.
- إذا تعذر حفظ الترخيص لا يبدأ الاستيراد، وإذا تعذر إرجاعه فلا يُعلن النجاح. لا ضمان لإرجاع ترخيص إلى DB مفقودة/غير قابلة للكتابة؛ تعاد نتيجة فشل صريحة، ولا يوجد تراجع آلي كامل لكل DDL أو استعادة بيانات تلقائية.

مصدر 2.6.9 هو السياق المجمد من الصورة السابقة، مع تغيير ثلاث دوال أصلية فقط: `_native_mysql_restore` و`restore_backup` و`_restore_backup`، وإضافة مساعد حماية الترخيص والوحدة المستقلة. بقي ماسح metadata الأصلي لـ2.6.9؛ لا `heavy_operation` أو اعتماد `services.sql_import_stream` من 2.7.0 داخل الصورة.

حُفظ الإصلاح كذلك في مصدر تطوير 2.7.0 الحالي دون بناء صورتها أو نشرها. لم تُنقل تحسينات ذاكرة PDF/Excel أو جامع التقارير أو تغييرات 2.7.0 الأخرى إلى هذه الصورة.

## الاختبارات على البنية النهائية

نجحت **67 حالة آلية داخل الصورة المترجمة**: 27 لتحليل SQL و15 للاحتفاظ والضغط و25 للنقل بمواصلات محاكاة، إضافة إلى **8 حالات معاملات SQLite** لحماية الترخيص في المصدر. اختُبر المساعد المترجم أيضًا على SQLite فعلية؛ ثَبُت أن ثنائي `backup_service` في البنية النهائية مطابق للثنائي الذي اجتاز هذا الفحص.

كل اختبارات MariaDB كانت في شبكة داخلية محلية دون منافذ منشورة، وبنفس الإصدار `10.11.19` وbinlog غير مفعل، مع حسابات تملك قاعدتها فقط دون `SUPER` أو `SET USER` عامة. الأوقات التالية تشمل تهيئة fixture؛ بعضها تزامن في التشغيل وليست مقارنة سرعة أو زمن واجهة HTTP.

في حالات النجاح حُفظت هويتا ترخيص اصطناعيتان محليتان وحقولهما المختبرة كما هي، بما فيها صف suspended. الحزم الاصطناعية لا تحمل توقيع ناشر معتمدًا؛ هذا فحص حفظ بيانات، وليس إصدارًا أو تفعيلًا لدى الناشر أو اختبار ترخيص عميل فعلي.

قورنت النتيجة مع استيراد مرجعي بلا معالجة البيانات: أعداد **18 جدولًا** متطابقة، و**17 جدولًا بكل الأعمدة** متطابقة، بما فيها المال والمبيعات والفواتير والمشتركون. الاختلاف الوحيد في جدول الكروت هو ملء `global_seq_id` لـ1,128 قيمة كانت NULL بواسطة المعالجة الحالية؛ صفر رقم موجود تغير، وصفر فرق رصيد. الشعار المستعاد مطابق ببصمته. لا HEX للأرقام في إثبات الدقة المالية.

مقارنة SQL بايتًا ببايت للملف الأصلي والملف الكبير أثبتت أن التغييرات محصورة في ستة تعريفات مالك فقط لكل ملف؛ كل بيانات INSERT وبقية SQL مطابقة. لا OOM في الحالات الفعلية النهائية ضمن حدود الحاويات 1GiB لكل من DB والعامل.

الاختبارات استدعاء فعلي للخدمة داخل الحاوية؛ ليست رفعًا كبيرًا من متصفح عبر Cloudflare. لم تختبر حزم RADIUS من NAS على الصورة الجديدة؛ Core ومسارات المصادقة الأخرى لم تتغير. نجاح مصادقة m بعد إصلاح DB السابق موثق في تقريره المستقل، ولا يُعاد وصفه كاختبار لهذه الصورة.

## ربط لوحة المنظومات الجديدة

سُحبت Web إلى السيرفر الجديد بالبصمة المثبتة وتحققت طبقاتها. ثم تغير **`releases.2.6.9.web` فقط** في كتالوج المنفذ؛ بقي الافتراضي `2.6.9` وCore `9786df38bb3c` وجميع الإعدادات الأخرى كما هي.

حُجز قبول الطابور بمعاملة SQLite قصيرة، وثبت خلو المهام الجارية/المنتظرة، ثم أعيد تحميل `max-host-r` مرة واحدة. لم تقطع مهمة جارية. لوحة التحكم وNginx بقيتا بنفس PID، والحاويات **التسع** السابقة بنفس صورها وأوقات تشغيلها وعدد إعادة التشغيل. بقيت بصمات **ثمانية ملفات محمية**، تشمل ربط المنظومات والأنفاق، ثابتة.

تحققت `inventory.release_catalog` التي تقرؤها الواجهة ومسار اختيار الإنشاء الافتراضي من نفس Web الجديدة وCore الثابتة. لم يُستدعَ إنشاء حقيقي أو إصدار ترخيص تجريبي على السيرفر؛ تحقق اختيار الإصدار دون حجز منظومة. استجابت `control.max-r.cc/login` و`m.max-r.cc/login` بـHTTP200 من الخارج.

**الاستعمال:** من المنظومات ← إنشاء منظومة، اختر `2.6.9` الافتراضية؛ المنفذ يستخدم البصمة الجديدة. الحجوزات والمنظومات القائمة لم تُغيّر صورها، بما فيها m التي أصلحت قاعدة بياناتها سابقًا. لا إعلان أو تحديث عبر اللوحة للمنظومات القديمة.
