# مرشح محرك تحديث المكونات — قبول محلي، 29 أكتوبر 2026

## نطاق الطلب والحالة

طلب الإنسان تطوير واختبار إصلاح المحرك مستقلًا أولًا، مع احتمال توزيعه قبل 2.7.0. التنفيذ الحالي **مرشح opt-in مستقل** في `services/system_update_components.py`، وليس قدرة معلنة في قناة التحديث القائمة. بروتوكوله 4؛ بقي `ENGINE_PROTOCOL=3` وعقد Web/Core الحالي دون تغيير. لا إصدار إنتاجي جديد أو إعلان أو رفع Registry أو تعديل عميل/دومين أو لوحة قديمة/جديدة.

لا يصح اعتبار هذا التقرير شهادة أن صفحة التحديث الحالية تستطيع تنفيذ كل المكونات الآن. تسليم المرشح عبر المحرك السابق وربطه باللوحة والقناة وتوفير سجلات الملكية في البيئات الفعلية ما زال قبولًا لازمًا قبل نشر تحديث مستقل. لا يعاد فتح نطاق تطبيق 2.7.0 أو اللوحة المتوقف تلقائيًا.

## ما نُفذ

- عقد موقّع قصير العمر بهوية جهة التنفيذ والمضيف/المنظومة، وإصدار سجل التبعيات وبيان المنظومات المتأثرة. لا مسارات أو shell أو SQL أو mounts حرة في البيان.
- سجل ملكية عند المضيف يربط كل مكون بدور Web/Core/DB/L2TP/Autoheal ومشروع Compose وخدمته وملفه وصور مثبتة بعقود توافق بيانات معتمدة محليًا. لا يستنتج التوافق من رقم التطبيق أو latest أو ادعاء الإصدار وحده.
- حدود تنفيذ منفصلة للمنظومة والمضيف. تعديل DB يتطلب وسم ملكية مُجهزًا صراحة؛ المحرك المشترك يرفض من صلاحيات المنظومة المنفردة. المنظومات المتأثرة تحسب من التبعيات، ويُرفض حذف أي منها من المشاركين.
- قفل العملية وحواجز `dispatch.lock` متوافقة مع المحرك السابق لكل منظومة متأثرة؛ تمنع الصيانة المشتركة عند وجود عامل تحديث قديم جارٍ أو غير متحقق.
- نسخة احتياطية إلزامية متحققة لكل منظومة متأثرة، وتجميد هويات الخدمات وإعداداتها والشبكات والتخزين قبل التبديل، وتحقق ثان بعد النسخ.
- اشتراط تخزين Web الدائم ورفض إسقاط كود فوق الصورة، مع مقارنة بصمات معرّف الجهاز والمنظومة ومفتاح الترخيص ومفتاح جلسات Web قبل وبعد؛ لا تُعرض القيم أو المفاتيح نفسها.
- إيقاف Autoheal التابع قبل تبديل DB والعملاء، ثم بدء التبعيات قبل Core/Web وإعادة المراقب. لا تترك المراقب يعيد خدمات قديمة أثناء التبديل.
- تعديل مقيد لبيئة DB (`MALLOC_ARENA_MAX=2`) وخيارات MariaDB المحددة في العقد. حفظ التغييرات في Compose مع مقارنة النسخة الحالية ورفض تعديل مشغل آخر، ودعم نهاية الأسطر CRLF.
- صور جديدة من allow-list موقّعة ومثبتة، مع رفض تبديل الصورة إذا لم يثبت توافق الصورة الحالية والمرشحة بعقد المضيف. لا ترقية رئيسية أو رجوع بيانات غير متوافق بشكل عام؛ يحتاجان خطة منفصلة مثبتة.
- حاوية DB بديلة تستخدم نفس التخزين الدائم؛ لا استعادة SQL عند الرجوع. تُحتفظ الحاويات الأصلية، وتُوقف المرشحات قبل استعادة التبعيات، وتُفحص النتيجة قبل `rolled_back`. ضياع رد الإنشاء يُراجع بالاسم ووسم المهمة والمكون؛ الانقطاع الملتبس لا يعاد تشغيله تلقائيًا.
- فحوص افتراضية ثابتة: Web بالتوقيع والترخيص والـlease ومرجع المحاسبة وإصدار التطبيق المتوقع، DB بفحص socket أصلي، Core بمنافذ RADIUS، وL2TP/Autoheal بعقد health مثبت في الصورة. هذه الفحوص وحدها ليست إثبات مرور نفق أو معاملة NAS كاملة.

## الفحوص المعزولة والصورة

نجحت 34 حالة جديدة داخل Linux، و34 مثلها داخل صورة اختبار مستقلة بملفات Python bytecode ودون source mount. تشمل التوقيع والجمهور والانتهاء وتغير سجل الملكية والصلاحيات ونطاق DB المشترك والنسخ لكل مشارك والتوافق وحواجز التحديث القديم وإيقاف Autoheal حتى لتبديل Web وحدها وضياع الرد والتكرار والرجوع وفشله وCRLF وأدوار الصور الخمسة وتخزين الهوية ورفض إسقاط الكود. قُوي فحص DB إلى `SELECT 1` موثق بدل ping الذي قد يدل على حياة الخادم رغم رفض الاعتماد، مع دعم متغيرات كلمة المرور وملفها المعتادة دون وضعها في argv.

نجحت أيضًا مجموعة `test_update*.py` المرتبطة: 87 حالة، منها حالة متجاوزة (تضم 29 من الحالات الجديدة قبل إضافة انحدار ضياع الرد الأخير)، و32 حالة `test_control_update_consumer.py`. لا تجمع هذه الأرقام كحالات فريدة؛ هناك تداخل وإعادات مقصودة. لم تشغل كل tests.

صورة الاختبار النهائية `max-radius-engine:protocol4-local-20261029-r5` مبنية على صورة Web المنشورة `c5ab9fe42359…` مع ملفات المرشح واختباراته فقط تحت `/opt/max-engine-candidate`؛ لم تدمج ميزات 2.7.0. الهوية التي أعادها `docker image inspect`: `sha256:b834e621aab644e198356ba480781180e8e7af0d967b86e6c6f04aba417c6130`. تطابقت بصمات الملفات الثلاثة المجمدة مع المصدر الحالي. ليست صورة إصدار موقعة نهائية ولا رقم إصدار تطبيق جديدًا، ولا يكفي نجاحها لتوزيع إضافة خارج قائمة الحماية الحالية. الصورتان السابقتان r3/r4 اجتازتا 30/31 حالة قبل آخر حواجز الهوية.

## قبول Docker/MariaDB

المشغل `tests/run_update_components_lab.py` ينشئ شبكات داخلية بلا منافذ مضيف، وحجوم DB وحاويات مستقلة موسومة بالجولة. الصور مثبتة: Web `c5ab9fe42359…` وMariaDB `0d0945c57f75…`. البيئة المحلية والدومين متماثلتان في تركيب Docker الخاص، والمحرك المشترك يضم قاعدتين منفصلتين لاثنتين من المنظومات مع Core/Web مستقلين.

المصفوفة تختبر النجاح وفشل Web بعد بدء DB وضياع رد إنشاء الحاوية، لكل تركيب. تتغير إعدادات تخصيص الذاكرة والكاش فعليًا ويُقرأ `@@global` من MariaDB؛ وفي الرجوع تتحقق الإعدادات الأصلية. يستدعى النسخ الحقيقي `backup_service.create_backup` من الصورة المنشورة لكل مشارك. تُكتب بيانات جديدة بعد النسخة الاحتياطية في جدول اصطناعي بمال وعدادات أكبر من 32 بت؛ الرجوع يجب أن يحفظها دون DB restore.

فحوص التوقيع/الترخيص وCore/NAS في هذه المصفوفة حقن مختبري معلن؛ خدمات Core/L2TP/Autoheal البديلة عمليات fixture، لا تثبت تحديث أنفاق أو watchdog حقيقيين. اختبار تبديل الصور الخمس حتى الآن محاكاة Docker بالعقد، لا تبديلًا حيًا لجميع صور المنتج. نتائج هذه المصفوفة لا تثبت Registry أو تحديث MariaDB إلى إصدار آخر.

اكتملت المصفوفة الأولية في الجولة r4 بنجاح: 9 حالات، بواقع نجاح واحد ورجوعين متحققين لكل تركيب محلي/دومين/مشترك. في المشترك نسختان إلزاميتان وفحص كلا قاعدتي المنظومتين. الإعدادات الفعلية والبيانات الأحدث محفوظة، ولم تتغير هويات وإعدادات وحالات الحاويات السابقة. أزيلت جميع حاويات وحجوم وشبكات الجولة. هذه جولة سابقة لتشديد فحص SQL وتخزين الهوية؛ لا تحل محل قبول الصورة النهائية أدناه.

## قبول FreeRADIUS الإضافي

اكتملت جولة مصدر إضافية `component-engine4-radius-20261029-r3` على محرك مشترك لقاعدتين مع حاويتي Core أصليتين بالصورة `bc4d46441080…`، وليستا عمليتي sleep. الحالات الثلاث: نجاح، ورجوع بعد رفض Web، وضياع رد create. نجحت 32 استجابة من FreeRADIUS: مصادقة وStart وInterim وStop؛ وثبتت في SQL جلسة واحدة نهائية لكل حساب اصطناعي، والعدادات 64 بت ورصيد 17.25 دون تغيير. احتفظ الرجوع بالبيانات الملتزمة بعد النسخ. أزيلت جميع موارد الجولة وثبتت هويات وحالات الحاويات السابقة.

هذه مصادقة RADIUS ومحاسبة SQL فعليتان مع عميل `radclient`، لكن سجل الترخيص/lease مُجهز اصطناعيًا في قاعدة المختبر، وليس ترخيصًا موقعًا مقبولًا من خادم التراخيص. لا RouterOS ولا جلسات Hotspot/PPPoE أو مرور نفق فعلي. الرسائل أرسلت قبل توقف المكونات وبعد عودتها؛ لم تختبر استلام رسائل NAS أثناء نافذة توقف DB/Core أو إعادة محاولاتها. إعادة تشغيل DB تتضمن انقطاعًا مقصودًا للخدمات التابعة، ولا نعد بعدم انقطاع المصادقة أو عدم ضياع أي رسالة خلاله دون قبول حركة NAS الحقيقية.

## قبول الصورة النهائية r5 دون ملفات مصدر

في `PRIVATE/component-engine4-final-compiled-20261029-r1` اختبرت الصورة المجمدة نفسها مع فحوص SQL المصادق وتخزين الهوية وبصماتها، وحجز منفرد تسلسلي دون تداخل فحص آخر. المصفوفة النهائية تجمع فحص الهوية الحقيقي وFreeRADIUS/SQL الحقيقيين، مع بقاء الترخيص fixture والأنفاق/Autoheal عمليات مختبرية:

| التركيب | الحالة | النتيجة | رسائل RADIUS الصحيحة | النسخ الإلزامية |
|---|---|---|---:|---:|
| محلي بقاعدة مستقلة | تطبيق إعدادات DB | completed | 5 | 1 |
| دومين بقاعدة مستقلة | تطبيق إعدادات DB | completed | 5 | 1 |
| محرك مشترك لمنظومتين | تطبيق إعدادات DB | completed | 10 | 2 |
| محرك مشترك لمنظومتين | فشل Web بعد التزام بيانات أحدث | rolled_back متحقق | 12 | 2 |
| محرك مشترك لمنظومتين | ضياع رد create قبل start | rolled_back متحقق | 10 | 2 |

الإجمالي 42 استجابة صحيحة وثماني نسخ احتياطية متحققة. في جميع الحالات بقيت بصمات machine/instance ومفتاح توقيع الترخيص ومفتاح جلسات Web ثابتة لكل منظومة، وحُفظت البيانات الأحدث دون استعادة SQL، ورفض فحص DB كلمة مرور خاطئة. قرئت أحجام الكاش من MariaDB الفعلية بعد التطبيق والرجوع؛ لا ادعاء قياس وفر RAM في هذه الجولة. اختبار حقن الفشل في المحلي والدومين موجود بالمصفوفة السابقة والمحاكاة؛ لم تكرر كل فروعه على الصورة النهائية، إذ ركزت فروعها الفعلية على تركيب المحرك المشترك الأوسع.

اكتملت الجولة النهائية وخروج المشغل بنجاح، مع `preexisting_identity_state_unchanged=true` وصفر حاويات/حجوم/شبكات تابعة متبقية. تحققت أيضًا خلو موارد الجولات التشخيصية السابقة بحسب وسوم مالكها، وحُفظ `ROOT-SUMMARY.private.json`. صور الاختبار والأدلة محفوظة محليًا؛ لا مراقب أو عامل خلفي متبقٍ من الجولة.

## أخطاء كشفتها الجولات قبل القبول

1. أول جولة لم تتجاوز إعداد schema لأن خروج التشخيص لم يكن JSON فقط. وثقت وأزيلت مواردها دون تبديل منتج.
2. الجولة التالية كشفت اعتماد fixture على socket المؤقت أثناء تهيئة MariaDB قبل جاهزية TCP. عولج انتظار اتصال fixture فقط؛ لم تعد المحاولة نفسها.
3. جولة لاحقة نجحت في النجاح والرجوع، ثم كشفت خللًا حقيقيًا في المرشح عند ضياع create قبل start: محاولة التحقق من IP لم يخصص بعد تمنع الرجوع. أصلح مسار تفكيك المرشح غير المبدوء وأضيف اختبار انحدار محدد؛ النتيجة القديمة `recovery_required` محفوظة وليست نجاحًا.
4. صورا تجميع أوليتان لم تنجحا في bootstrap namespace/path. الصورة r3 صححت مسار الاستيراد، واجتازت الحالات الثلاثين دون ملفات مصدر. لا تُعتبر الصور السابقة مقبولة.
5. تجهيز RADIUS الأول أخفق قبل التنفيذ لأن singleton الخاص بالـlease ينشأ أثناء التهيئة. صُححت بيانات fixture لتحديث صفه الموجود بدل إدخاله مرتين، بجولة جديدة؛ لم يعد تشغيل الجولة المالية نفسها أو تجاوز حماية ترخيص إنتاجية.
6. الجولة المجمعة `radius-compiled-...-r1` أنهت الحالات الثلاث والـ32 استجابة وفحص الاعتماد الخاطئ، لكن فشل شرط ثبات الجرد أثناء تزامن حاوية فحص مؤقتة أخرى مع التقاط المرجع؛ سجلت `preexisting_identity_state_unchanged=false` ولا تعتمد لقبول العزل. أضيفت كذلك شروط تخزين الهوية وفحص بصماتها وأعيد القبول النهائي تسلسليًا بصورة r5 وبيانات جديدة؛ لا يُغيّر الإيصال السابق إلى نجاح.

الأدلة الخاصة خارج Git: `PRIVATE/component-engine4-local-20261029-r1` إلى `r4`، و`PRIVATE/component-engine4-build-20261029-r1` إلى `r3`، و`PRIVATE/component-engine4-radius-20261029-r1` إلى `r3`، و`PRIVATE/component-engine4-radius-compiled-20261029-r1`، و`PRIVATE/component-engine4-final-compiled-20261029-r1`. لا تعاد الجولات المكتملة أو غير المتيقنة، ولا يُحذف سجل الفشل لمنح إعادة محاولة.

## ما يلزم قبل الإرسال المستقل

- إنهاء ربط اختيار/تسليم الحزمة الموقعة مع اللوحة والقناة، وقبول انتقال واحد من المحرك المنشور إلى المرشح من الزر المعتاد؛ لا نشر مراحل تحضيرية جديدة لكل تحديث لاحق ضمن العقد المعتمد.
- تجهيز تسجيل الملكية والصلاحيات عند الإنشاء في المحلي والدومينات والمضيف المشترك، مع خطة انتقال واضحة للموجود. سجل خاص فارغ أو ناقص لا يمنح تحكمًا بالمضيف.
- قبول الترحيلات القائمة مع عقد المكونات دون تشغيل DDL حر أو تخطي خطة التوافق. المرشح الحالي يدير المكونات والإعدادات؛ ترحيلات المخطط المعتمدة تبقى في المسار السابق حتى قبول دمجهما.
- قبول الصور الأصلية لـCore/L2TP/Autoheal والأنفاق عبر حركة فعلية، واختبار RADIUS/Accounting والترخيص الموقع بعد التبديل والرجوع، وقطع العامل/المضيف والحمل الممتد. اكتشاف فشل أو تراجع موثق لا يعد نجاحًا تشغيليًا بحد ذاته.
- إنتاج صورة إصدار نهائية ضمن حماية المنتج، وتثبيت هويتها ومكونات التغليف واختبار تسليم المتحكم نفسه. لا تعميم ضبط DB أو تقدير وفر RAM على المضيف من مجرد نجاح دورة التبديل.
