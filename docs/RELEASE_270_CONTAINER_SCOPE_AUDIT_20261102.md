# نطاق حاويات 2.7.0 والاستضافة والمحركات المشتركة — 2 نوفمبر 2026

هذه مراجعة قراءة فقط للمصدر، وإيصالات البناء، وRegistry، وإعدادات المضيف الجديد. لم تُبنَ صور، ولم تُسحب طبقات جديدة أو تُرفع، ولم يتغير دومين أو كتالوج أو إعداد DB أو لوحة. القيم الحية أدناه لقطة وقت المراجعة وليست مراقبة مستمرة.

## النتيجة التنفيذية

التحديث الكامل أوسع من إصلاح الهوية الأخير. يلزم إصدار Web جديدة لكل منظومة، وخطة إعداد ذاكرة DB مستقلة على مستوى المحرك، وربط كتالوج وإنشاء وتحديث اللوحة الجديدة. Core المرشحة تحفظ آخر Core مرفوعة من 2.6.9 دون تغيير ملفات تشغيلها؛ استبدالها يتوقف على صورة Core المثبتة فعليًا في كل منظومة وقرار توحيد التغليف. لا توجد حاجة مثبتة إلى تحديث صور الأنفاق أو Autoheal أو خادم الترخيص أو Nginx من أجل نطاق 2.7.0 الحالي.

## تحسين الرام: كود Web مقابل إعداد المحرك

تحسين الجامع والتقارير والتصدير والاستيراد والاستعادة في Web يقلل الحمل والمواد الوسيطة. هذه التحسينات لا تضبط allocator أو الكاش في MariaDB.

المصدر يحتوي خطتين اختياريتين في services/db_memory_profile.py وdeploy/db-memory:

1. balanced: يضيف `MALLOC_ARENA_MAX=2` بعد إثبات allocator المتوافق، ويترك أحجام الكاش وInnoDB كما هي.
2. conservative: الإعداد السابق مع Aria16MiB وkey buffer8MiB. يبقي InnoDB والمتانة والبيانات والشبكات والصورة؛ يحتاج قبول أثر I/O والأداء قبل تعميمه.

لا يتطلب ذلك ترقية MariaDB10.11 إلى إصدار رئيسي آخر أو بناء صورة DB مخصصة. تغيير البيئة يحتاج إعادة إنشاء DB مع نفس التخزين والصورة والإعدادات المحفوظة؛ تعديل ملف إعداد فقط قد يحتاج إعادة تشغيل وفق طريقة تثبيته. لا إسقاط cache أو swapoff أو حذف بيانات أو استعادة DB للتراجع.

قبول الساعة السابق استعمل InnoDB128MiB في مختبر محدود. هذا **ليس** قرارًا بخفض InnoDB الإنتاجية من512 إلى128؛ وفي المحرك المشترك يجب حساب مجموع حمل قواعده. لا ضمان لثبات RAM لأيام من اختبار الساعة، ولا مقدار وفر إنتاجي مضمون.

## فجوات الربط التي يجب إكمالها

مصدر اللوحة في max_saas_panel_v2_local/backend/hosting_runtime.py طابق بصمة نسخة المضيف `57012c1d033c`. الدليل المباشر:

- update_release عندالسطر634 يقبل انتقال Web فقط ويشترط أن candidate.core يساوي Core المرتبطة بالمنظومة. تسجيل Core270 بدل9786 يمنع تحديث m من هذا المسار، رغم تطابق ملفات التشغيل. كما أن max مرتبطة في السجل بـCorebc4d القديمة، فتحتاج خطة انتقال Core مستقلة حتى عند اختيار9786 للكتالوج.
- يمكن دعم Web270 مع Core9786 للقواعد التي تحمل9786 فعليًا، مع اعتماد rollback_compatible والتحقق من الإصدار والترخيص. لا يبرر ذلك تجاوز رفض Core القديمة أو تغيير رقم الربط دون تغيير متحقق للحاوية.
- إعدادات MAX_CONTROL_MODE/SOCKET/TENANT_ID ومسار الوصلة المحدودة تمر إلى Web جديدة أو بديلة. يجب حفظ ذلك، مع UUID والترخيص والمفاتيح والتخزين والشبكات وpool والصلاحيات؛ لا Docker عام داخل Web المستأجر.
- محرك المكونات4 يدعم environment محدودة وmariadb_options مع توقيع وسجل ملكية يشمل جميع المتأثرين، لكن snapshot العام يطابق حاويات عبر Compose project/service. الحاويات الفعلية هنا تستخدم max.platform/max.tenant/max.service وmax.pool، بلا هويات Compose. نجاح fixtures المشتركة السابقة لا يثبت تسجيل هذه البنية الحية. يلزم محول ملكية صريح وربط مضيف أو خطة إعداد مضيف مستقلة متحققة؛ لا صنع labels مزيفة أو فتح تحكم DB للمستأجر.
- مخططdb_memory_profile الحالي يرفض صورة المحرك المثبتة بصيغةmariadb@sha256 وحدها، لأنه يتحقق من اسم إصدار10.11/11.8 في المرجع. أعيد رفض هذه الحالة بدالة التخطيط النقية. يلزم إثبات الإصدار والallocator مع الحفاظ علىdigest ثم تكييف عقد التخطيط؛ لا استبدال المرجع المثبت بوسم متغير لمجرد تمرير التحقق.
- ملفاتComposeالاختيارية تضبط خدمةmariadb؛ لا تطبق نفسها علىmax-db-a/bاللذين يديرهما منفذ مختلف. لا مسار إنتاجي مكتمل في اللوحة يطبق هذه الخطط بمجرد ترقيةWeb.

يمكن فصل تحديث Web لكل دومين عن ضبط المحرك المشترك. أما تغيير DB فينفذ مرة على مستوى المضيف، محركًا واحدًا في كل مرحلة، بخطة تشمل كل المشاركين والمهام الجارية ونافذة انقطاع SQL المتوقعة. نجاح HTTP/healthy ليس قبول المصادقة والمحاسبة؛ يلزم التحقق من رجوع SQL وتقدم المحاسبة ومصادقة فعلية متاحة، دون تجارب مالية غير مأذونة.

## ما بقي قبل اعتماد الحزمة الكاملة

1. تجميع Web النهائية من المصدر الحالي على الأساس المثبت، بما فيه إصلاح الهوية بعدr6، والتحقق من توقيعها وفروقها وفحوصها المرتبطة. لا يُنسب قبولr5/r6 تلقائيًا إلى الملفات المعدلة لاحقًا.
2. تثبيت سياسة Core: حفظ9786 حيث هي قائمة، أو قبول انتقال Core ضمن الحزمة المنسقة؛ ومعالجة المنظومات الأقدم دون افتراض مساواة رقم2.6.9 لصورة واحدة.
3. اختيار وقبول إعداد ذاكرة DB لكل بيئة؛ تثبيت جرد التبعيات والملكية والallocator، واختبار الأداء والتوقف والتعافي والرجوع على طوبولوجيا max-r الفعلية المعزولة.
4. إكمال ربط المنفذ والكتالوج وخطة تحديث/رجوع Web/Core وضبط DB، واختبار إنشاء منظومة جديدة والترقية من القائمة مع محرك مشترك وتعدد إصدارات، مع حفظ قواعد وحقوق بقية المستأجرين.
5. اعتماد النشر لاحقًا. هذه المراجعة ليست تفويض نشر ولا نتيجة تثبيت. لا تحديث لوحة قديمة أو خادم ترخيص أو أنفاق من هذا النطاق.
