## تعديل الحارس

- تثبيت هوية Docker والمضيف والصور والملكية وبصمات الملفات ونافذة التنفيذ قبل أي خطوة؛ لا يعتمد على الوسم أو رقم 2.7.0 وحده.
- نقل الأسماء والعناوين الثابتة في الاتجاهين؛ عند توقف الحاوية يراجع IPAM المحفوظ مع غياب مالك أجنبي للعنوان.
- حارس مستقل لمقطع الترحيل الحرج، وإلغاء بمهلة وفحص قبل/بعد SQL والـcommit، مع سجل مراحل يمنع الإعادة العمياء.
- رجوع مرة واحدة إلى الزوج الحالي مع **نفس قاعدة البيانات** دون DBrestore أو إعادة محاسبة قديمة. يُرفض الرجوع التلقائي بعد القبول أو تكرار محاولة الرجوع.
- القبول يتطلب ترخيصًا حديثًا وتقدم محاسبة ومصادقة، ويقرأ تعثر SQL الفعلي في FreeRADIUS؛ HTTP200 وhealthy وحدهما لا يكفيان. غياب حركة جديدة ينتج انتظارًا، لا حكم انقطاع.
- تأكيد العطل بعينة ثانية بعد ثانيتين. غموض الحالة أو تعطل DB المشتركة ينتج HOLD وتصعيدًا، لا تشغيل DB أو استعادتها تلقائيًا.
- بوابة توافق تاريخ الرجوع: Core الحالية لا تفهم التاريخ الملخص الجديد؛ يلزم أن يكون جدولا الملخصات والأختام فارغين قبل التجهيز وقبل الرجوع. القراءات المجهولة أو المحتوى غير الفارغ يمنعان التنفيذ ويحتاجان مراجعة؛ لا يُقبل الرجوع إلى Core قديمة بعد تلخيص حي.

## سبب منع التحديث

تأكيد لاحق قراءةً عند16:43عدن: Core الفعلية على **m.max-net.net** صورتها `04fd43b4e13f` وحاويتها `e61f791ab5d9`، وليست صورة r2 نفسها بالبصمة. لكن ملف `queries.conf` الفعلي مطابق بايتًا لملف الصورة المنشورة `8c5594cf7a89` (SHA256 `86d111f503ab0d2f71ecd4dfa2aa0d989b531a6cadd093d8c3d778a435545bab`، و11مرجعًا للعرض). أعيدت قراءة Registry وأكدت أن وسمr2يشير إلى `8c5594cf7a89`. لذلك **الكود المعني بالبطء موجود في الاثنين**، دون ادعاء تطابق الصور كلها أو قياس بطء فعلي على m بهذه الجولة. الإثبات `core-identity-querycheck.private.json` في جولة m المحمية؛ لا تغيير للخدمة.

على **نفس قاعدة البيانات** وبنفس طلب التفويض، مع حد `max_statement_time=2`:

| حد DB المحلي | استعلام Core الحالية | استعلام Core maintenance-r2 |
|---|---:|---:|
| 1.5GiB | 0.004727ث | تجاوز2.00276ث؛ خطأ1969 |
| 3GiB | 0.002955ث | تجاوز2.001619ث؛ خطأ1969 |

في `docker/freeradius/queries.conf` يستخدم `authorize_check_query` الجديد عرض `radacct_quota_owned` المبني على UNION في `database/usage_summary_schema.py`. خطة التنفيذ أثبتت materialization ومسحًا كاملًا لفرع محاسبة يقدر بنحو336 ألف سجل، مقابل استخدام فهرس `idx_subscriber_account_read` في المسار الحالي. هذه أرقام EXPLAIN تقديرية للصفوف، وليست عداد صفوف فعليًا ممسوحة.

ظهر في FreeRADIUS تعثر `authorize/sql` مع بقاء HTTP200 وhealthy والترخيص صالحًا. تحقق اتصال DB والإعدادات والتوجيه داخل المختبر، لذلك لا يصح تفسيره كفشل راوتر أو ترخيص. إضافة فلتر خارجي وحده جُربت قراءةً وتجاوزت المهلة أيضًا؛ ليست إصلاحًا معتمدًا، ومقارنة البيانات الناتجة عن استعلام أُجهض لا تثبت اختلاف النتائج.

المطلوب في الخطوة التالية: إصلاح مسار SQL ليقيد صفوف المحاسبة قبل materialization، مع إبقاء الملخصات والحصص والأختام ودورات الاشتراك صحيحة، ثم بناء صورة مثبتة جديدة وإعادة حمل المصادقة والمحاسبة والرجوع. لا يُستبدل الإصلاح بتغيير مهلة القبول أو الاكتفاء بصحة الحاوية.

## البيانات والملاحظات المحاسبية

المقارنة المباشرة قبل/بعد التبديل والرجوع حفظت بيانات المصدر الأصلية و11 مجموعة مالية ومرجعية بعد استبعاد `wisp_sale_sources.reviewed_at` فقط لأنه وقت مراجعة خلفية متغير. بنهاية الجولة الطويلة بقيت جميع57,553 كرتًا بلا فقد، وأسماء المستخدمين وكلمات المرور والأرصدة والحصص وسائر الأعمدة الأصلية مطابقة باستثناء تغيرات lifecycle المفسرة:

- 3,120 `global_seq_id` كانت NULL، ومُلئت وفق registry الموجود بآلية schema-healer الأصلية.
- 15 كرتًا انتقلت active→expired:14 بسبب التاريخ، وواحد تجاوز حصة367,001,600 بايت باستهلاك367,002,470 بايت. حُذفت بيانات radcheck لهؤلاء المنتهين فقط؛ صفر بيانات دخول محذوفة لغير المنتهين، ولا فقد في radreply/radusergroup.
- عدد ومجاميع محاسبة المصدر الأصلية مطابقة؛ لم يحدث rewind. لذلك لا ندعي تطابق بصمة كل صف كرت حرفيًا بنهاية وقت الاختبار الطويل.

## دقة المحاكاة وحدودها

العميل4vCPU وذاكرة6,767.18MiB وDB بلا حد حاوية. المختبر Docker Desktop/WSL بذاكرة7,793.17MiB؛ وُضعت حدود منفصلة للحاويات، وحد CPU لكل منها4 وليس حدًا إجماليًا للمضيف. DB المحلية بدأت1.5GiB وحدث OOM أثناء الضغط؛ الحارس أمسك الحالة دون استعادة أو إعادة تشغيل DB. جرى تعافٍ محلي صريح لنفس الحاوية والـvolume ورفع الحد3GiB، وأُعيد إثبات بطء الاستعلام. لا يُستنتج من OOM المحلي أن العميل سيتعرض له حتمًا. جلسة ذلك الاختبار أُغلقت وتحقق open=0.

صورة L2TP الأصلية استُخدمت لتوجيه UDP ثابت، دون PPP/MikroTik حي. Autoheal لم يشغّل داخل المختبر كي لا يتداخل مع حقن الأعطال. الترخيص اختُبر بجهة توقيع مختبرية معزولة، دون مفتاح الناشر أو جهة الترخيص الحقيقية؛ توليد إعداد الإنتاج أثبت غياب هذه الثقة المختبرية. لا إثبات مطابقة NAS فعلية.

أخطاء تجهيز المختبر (CRLF بدل LF، healthcheck الموروث، جذر أرشيف FreeRADIUS، عنوان مراقبة HTTP5090، وتعامل Docker مع IP للحاوية المتوقفة) صُححت وسُجلت قبل اعتماد إعادة الاختبار. الاستكمال استند إلى receipts ولم يُعد تشغيل ترحيل أو عمليات مالية مكتملة. فشل استيراد مرجع مقارنة أول حدث في schema معزولة فقط؛ المقارنة النهائية تمت على مرجع ثانٍ صحيح دون إعادة ضبط قاعدة التجربة.
