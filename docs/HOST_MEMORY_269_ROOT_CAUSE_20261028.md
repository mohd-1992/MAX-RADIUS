ذيل access.log المقروء محدود بآخر 2 MiB، من نحو 09:09 إلى 20:29 UTC؛ احتوى 14 طلبًا مصنفًا للمبيعات و27 مسارًا مصنفًا للتصدير/التنزيل/الطباعة. لا يكفي هذا لإثبات عملية تصدير ثقيلة أو إسناد كل طلب إلى دومين، ولا يغطي اليوم كاملًا. لا استنتاج بأن الرسم ظل مفتوحًا طوال اليوم. محاولتا جامع شاملتين لم تكتمل قراءتهما ضمن المهلة واستبعدتا؛ الأدلة المستخدمة جاءت من مجاميع أصغر مكتملة. لم تعد أي عملية تصدير فعلية.

## 4. عوامل أخرى مهمة في قراءة RAM

الفحص السابق [يفصل الكاش والـSwap](HOST_MEMORY_GROWTH_DIAGNOSIS_20261028.md): كاش m Web نحو 610 MiB وذاكرة anon نحو 228 MiB، وSwap المضيف أقل من أمس بنحو 705 MiB. خدمة journald تضم نحو 890 MiB صفحات ملفات لا ذاكرة خاصة للتطبيق؛ لا تجمعها فوق كاش المضيف مرة أخرى. تلك عوامل تجعل عبارة إن جميع الزيادة تسريب من تقارير 2.6.9 غير صحيحة.

محرك DB لم تبدل صورته أو بدء تشغيله مع تحديث Web الأخير، لكن SQL الذي يرسله Web تغير، ولذلك يمكن للتحديث رفع استهلاك DB دون تغيير المحرك نفسه. جميع المحركات الخمسة ما زالت ذات إعدادات افتراضية متشابهة ولا توجد حدود RAM لمعظم خدماتها؛ عدد الاتصالات الحالي المنخفض لا يثبت أن ذروة تقارير سابقة لم ترفع RSS.

عند 20:30:58 UTC بقي استخدام المضيف 53.09% مقابل 53.18% في أول فحص 20:15. ضغط PSI اللحظي صفر، وحاويات الإنتاج الـ19 ظلت بالهويات والصور وأوقات البدء وعدد إعادة التشغيل نفسها وحالتها التشغيلية healthy. هذا تحقق سلامة وحدود رصد، وليس إثبات مصادقة ومحاسبة كل عميل.

3. قبول التغيير بقياس تكرار حمل عادي وذروات محددة على بيانات أكبر، ومتابعة anon/RSS وswap ووقت SQL مع ثبات النتائج. اختيار حدود حماية DB/Web بعد قياس مناسب، لا تقليص DB أو إعادة تشغيلها دوريًا لإخفاء الأعراض.
