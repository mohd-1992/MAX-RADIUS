## ربط Web بالحاوية العاملة

استدعيت دالة الاختيار المجمعة داخل صورة Web المرشحة نفسها، أمام Docker حقيقي عبر وسيط قراءة مقيد بحاويات الجولة. تحققت هوية Web من التشغيل الفعلي، ومشروع Compose، ودور Core وحالتها ومعرفها؛ لا يعتمد القبول على الاسم أو HOSTNAME أو healthy وحدها.

| الحالة | النتيجة المثبتة |
| --- | --- |
| Web الجديدة أثناء بقاء Core القديمة عاملة | اختارت القديمة العاملة المقصودة |
| بعد التبديل مع الاحتفاظ بـCore القديمة متوقفة | اختارت Core الجديدة العاملة؛ لم تختر القديمة |
| Core من مشروع آخر وحاوية one-off موجودتان | تجاهلتهما |
| Core ثانية عاملة داخل المشروع نفسه | رفضت الاختيار لوجود التباس |
| لا Core مناسبة عاملة مع وجود صور وحاويات متوقفة | رفضت الاختيار؛ لم تستعمل متوقفة |
| HOSTNAME موروث من Web القديمة | بقي الاختيار مطابقًا لهوية التشغيل الحالية |
| العودة إلى المرشح بعد تجربة الرجوع | أعيد التحقق من Core الجديدة العاملة |

هذه **ست حالات قبول للدالة**؛ تجاهل الحاوية الأجنبية وone-off ضمن إعداد الحالات، وليس عددًا إضافيًا. أثناء الرجوع القديم تحقق عنوان Core ومعرفها وحالتها، ثم مرور RADIUS وحصة الحساب؛ لا تنسب دالة اختيار المرشح إلى نسخة قديمة لا تحتويها.

## تعطل DB واستعادة المحاسبة

أوقفت عملية حاوية DB الجديدة قسريًا بالمعرف المثبت، ثم شغلت **الحاوية نفسها وقرصها نفسه**. لم تستعمل نسخة احتياطية أو تخفض عدادات أو تعدل جلسة أصلية.

أرسلت أداة الاختبار حزمة Stop اصطناعية أثناء توقف DB. **لم يصل ACK خلال 12 ثانية**. عند القراءة بعد عودة DB، وقبل أي إعادة إرسال، كانت الحزمة الأصلية قد حُفظت: Stop فعلي وسبب User-Request والعدادات النهائية الصحيحة على الصف وUID نفسيهما. إعادة إرسال Stop مرتين لاحقًا لم تضاعف الاستهلاك. لم ترصد حالة ACK دون حفظ Stop في هذه التجربة.

تأخرت أداة انتظار الجاهزية لاستعمال اسم متغير اعتماد غير صحيح في fixture؛ صحح الانتظار فقط، دون إعادة افتعال العطل أو إعادة الحزمة الأولى. لذلك لا يستنتج من هذه الجولة زمن التعافي الأدنى، أو آلية صف/احتفاظ مضمونة في FreeRADIUS، أو نجاح جميع أنماط الانقطاع. إعادة الإرسال هنا برمجية صريحة، **وليست اختبار سياسة RouterOS الأصلي**.

## انقطاع طاقة الآلة الافتراضية مع بقاء القرص

استعمل الاختبار آلة QEMU محلية بلا شبكة، وجذر ملفات **صورة MariaDB 10.11.19 نفسها**، وقرص ext4 ثابتًا. البيانات داخلها اصطناعية فقط؛ توافق بيانات العميل اختبر في حاويات اللقطة المنفصلة. اختبرت خسارة كاش نظام تشغيل الضيف بإنهاء QEMU قسريًا، ثم الإقلاع من القرص نفسه، وليس مجرد إيقاف عملية MariaDB. لم يطفأ مضيف العميل أو المضيف المشترك أو قرصهما.

| الإعداد | معاملات COMMIT مؤكدة بسجل شاهد خارج الضيف | بعد التعافي | قياس 150 كتابة مستقلة محليًا |
| --- | --- | --- | --- |
| `innodb_flush_log_at_trx_commit=2` | 40 | جميعها موجودة؛ الرصيد والعداد متسقان؛ المعاملة غير المؤكدة لم تحفظ؛ CHECK TABLE صحيح | متوسط 1.129ms |
| `innodb_flush_log_at_trx_commit=1` | 40 | جميعها موجودة؛ الرصيد والعداد متسقان؛ المعاملة غير المؤكدة لم تحفظ؛ CHECK TABLE صحيح | متوسط 8.380ms |

كان doublewrite مفعّلًا وbinary log معطلًا في الحالتين. لا فقد مرصود في هاتين العينتين، لكن نجاح commit=2 مرة لا يحوله إلى ضمان دوام عند انقطاع الطاقة. خيار commit=1 اجتاز الاختبار وكان أبطأ؛ قياس QEMU المحلي لا يتنبأ بأداء قرص العميل أو حمله.

تعثر تجهيز الضيف أولًا بسبب تركيب الجذر للقراءة فقط، ثم سطر تشغيل CRLF، ثم غياب تعريف localhost في `/etc/hosts` المستخرج من صورة Docker. احتفظت الأدلة والمحاولات، وصححت تجهيز ضيف الاختبار وحده. لم تبدأ معاملات الشاهد قبل نجاح الإقلاع، ولم تعد جولة معاملات مؤكدة مكتملة.
