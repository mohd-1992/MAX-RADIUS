# تصحيح فاتورة البوابة وسجل تعديل المشترك — 24 أكتوبر 2026

التصحيح في المصدر المحلي فقط، دون بناء صورة أو رفع أو تحديث 5090 أو أي دومين أو عميل. قواعد البيانات والاعتمادات والتراخيص الحالية لم تُعدّل.

## الفاتورة

`user_portal_service.renew_or_change_package` ينشئ الآن فاتورة للمشترك بسعر الباقة الجديدة وحالة paid، واسمها ووقت الدفع المطابق لبداية الدورة. الإدراج داخل المعاملة والقفل نفسيهما اللذين يحفظان خصم المحفظة والعقد وRADIUS. فشل الفاتورة يعيد الخصم والعقد وبيانات RADIUS معًا. يتشارك مسارا التجديد وتغيير الباقة في البوابة هذه الدالة. الكرت يظل يسجل بيعًا في wisp_voucher_sales؛ لا يُنشأ له صف فاتورة مشترك بمعرف متداخل.

لم يتغير حساب الحصة أو الترحيل أو تسوية الجلسات، ولا أُنشئ مفتاح منع إعادة طلب جديد للبوابة. القفل يمنع التداخل؛ لا يعني منع كل شراء مستقل لاحق. لم تُنشأ فواتير رجعية لخصومات قديمة؛ لا يكفي غياب الفاتورة وحده لإعادة تنفيذ شراء أو افتراض مبلغ مستحق.

## سجل التعديل

كانت edit_subscriber تسجل EDIT_CONTRACT بصيغة JSON لكل حقول العقد، وتستدعي update_subscriber الذي يسجل UPDATE_PROFILE أيضًا. القالب كان يعرض القيم الخام ورموز الإجراءات. أصبح مسار التبويب يسجل إدخالًا واحدًا يضم الحقول المتغيرة فقط، ويحتفظ بسجل النظام العام في المعاملة نفسها. سجل الملف الشخصي القديم يبقى افتراضيًا عند استعمال update_subscriber مباشرة؛ تعطيله محصور باستدعاء التعديل المركب الذي يسجل الإدخال البديل.

`subscriber_audit_service` يجمع فروق العقد والبيانات الشخصية، ويستبدل قيم كلمات المرور بعلامة changed. القراءة تعرض تسميات عربية وسطور «من … إلى …»؛ ولا تعرض كلمات المرور حتى لو احتواها JSON تاريخي. القالب يستمر في escaping للأسماء والقيم، ودون safe أو HTML من السجلات. الحفظ دون تغيير لا يعيد مزامنة RADIUS ولا يولد سجل تعديل وهميًا، لكنه يحفظ إيصال الطلب. إعادة الإيصال نفسه لا تولد سجلًا آخر.

السجلات القديمة المزدوجة لم تُحذف أو تُخفَ بتخمين ارتباطها؛ أصبحت تفاصيل JSON فيها مقروءة عند العرض مع إخفاء الحقول غير المتغيرة، بما فيها NULL مقابل الربط الفارغ. الحقول الشخصية التي لم يسجلها JSON القديم لا يمكن استعادتها بأثر رجعي.
