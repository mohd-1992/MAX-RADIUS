# استكمال محاكاة CLIENT_AS محليًا — 3 نوفمبر 2026

تحديث لاحق: [اختبارات الأعطال المتبقية وقبول الحارس المعدل](CLIENT_AS_270_GUARD_FAULT_ACCEPTANCE_20261103.md) كشفت استمرار عامل الترحيل بعد فقد المتحكم، وأغلقت الحالة بحزمة محلية معدلة مع إعادة الاختبار. لا يعتمد الحارس الأصلي لهذا التقرير؛ التقرير اللاحق هو مرجع اعتماده، مع حفظ نتائج الصور والبيانات أدناه.

اكتملت الاختبارات المحلية الإضافية للانتقال اليدوي من 2.6.5 إلى 2.7.0 والرجوع. ثبتت سلامة البيانات المختبرة والتشغيل بعد العمليتين، لكن **لا تعتمد الخطة باعتبارها انتقالًا أو رجوعًا بلا انقطاع**. احتاج ترتيب الترحيل والرجوع إلى تعديل في مشغل المحاكاة المحلي؛ الصور المنشورة لم تتغير. لم يُحدّث العميل أو أي دومين، ولم يُرفع كود أو صورة أو يُغيّر ترخيص إنتاجي.

هذا التقرير يستكمل [جولة البيانات والمالية والاستعادة السابقة](CLIENT_AS_270_LOCAL_REHEARSAL_20261102.md) ويتقدم عليها في موضوع الحمل أثناء أول DDL، وعقد التشغيل الفعلي، والتحقق الإضافي من الترخيص. نتائجها السابقة ليست إعادة تنفيذ جديدة في هذه الجولة.

## النطاق والأدلة

- المصدر هو اللقطة المتسقة السابقة للعميل: 51,432 كرتًا و317,794 سجل محاسبة. المدخلات SQL وstorage وإعدادات Core مثبتة بالبصمة، وليست بيانات مولدة بدل بيانات العميل. حسابات الحمل والترخيص التجريبي إضافات معزولة.
- الصور نفسها: Web القديمة `5eda6a3450dd` وCore القديمة `7bf2baa71525`، وWeb الجديدة `5455db7ca85a` وCore الجديدة `10cc88946c5e`، تحت `2.7.0-20261102-r1`. البصمات الكاملة في التقرير السابق والإيصالات المحمية؛ لا اعتماد على latest.
- MariaDB 10.11.19 نفسها دون تغيير صورة، وبإعدادات ذاكرة المصدر. المطلوب لاحقًا استبدال Web وCore مع تهيئة SQL وحفظ تخصيصات Core وعقد التشغيل، لا استبدال DB/L2TP/Autoheal.
- المختبر Docker Desktop المحلي، شبكة داخلية دون منافذ منشورة أو NAS أو جهة ترخيص إنتاجية. حافظ على Entrypoint وCmd وHealthcheck وCapAdd وRestartPolicy وأهداف الربط من تعريف الحاوية الفعلي. ترجمت عناوين وأسرار الشبكة إلى نظائر مختبرية، مع حدود RAM/CPU موثقة سابقًا؛ ليس جهاز العميل أو نواته أو تخزينه.
- الأدلة خارج Git تحت الإحالة PRIVATE في ENVIRONMENTS: `client270-followup-20261103-r1` للتشخيص والترخيص، و`client270-bounded-20261103-r1` لعزل أثر MAC، و`client270-finalplan-20261103-r1` للخطة النهائية. لا تنقل ملفات SQL أو الاعتمادات أو sitecustomize أو جهة التوقيع التجريبية إلى حزمة إنتاجية.

## الاكتشافات الفعلية ومعالجتها في الخطة المحلية

### المصادقة أثناء أول ترحيل

التشغيل المباشر للتهيئة الأصلية مع حمل RADIUS أعطى 11 فشلًا للمصادقة الصحيحة من 658 طلبًا: مهلة واحدة وعشرة Access-Reject. قبل الترحيل وبعده كانت الحالات ناجحة، والمحاسبة بقيت مطابقة. لذلك لم يُعتمد هذا التسلسل المباشر.

وجد سببان منفصلان:

1. مثبت MAC الأصلي يقرأ الحسابات الناقصة بقفل `FOR UPDATE` دفعة كبيرة. تجربة قفل مستقلة على جداول ظل أثبتت خمس مهل SQL 1205 عند انتظار حساب مقفول. استخدم التحضير المحلي المثبت المترجم نفسه على دفعات لا تتجاوز 256 حسابًا، مع نفس التطبيع والقواعد. لم يُعدّل ملف داخل الصورة.
2. مثبت سعة الترخيص الأصلي يبطل runtime lease عمدًا عند تغير تعريف الدوال/التريغرات. دورة النشر الدوري التالية تعيدها بعد التحقق؛ أثناء الفاصل يرفض RADIUS المصادقة. بعد تقسيم MAC وحده بقي 14 Access-Reject في 726 طلبًا، دون مهلة، فالتقسيم وحده لا يحل السبب الثاني. تجربة مضبوطة باستدعاء المثبت الفعلي ثم ناشر الترخيص الفعلي أثبتت الإبطال والرفض ثم استعادة القبول.

الخطة المحلية النهائية تضيف حاجزًا قصيرًا عند تغير مخطط السعة: تثبيت هوية Core ثم SIGSTOP للعملية المعزولة، تصريف استعلاماتها، تنفيذ المثبت الأصلي بإبطاله الأصلي، ثم النشر والتحقق الأصليان من التوقيع والهوية والصلاحية. يتحقق المتحكم أيضًا من دالة الترخيص SQL قبل SIGCONT. لا كتابة عمياء لـis_valid، ولا تمديد يدوي للترخيص أو تجاوز للتوقيع.

حارس مستقل مقيد بهوية المضيف والحاوية والصورة وPID/starttime يستأنف Core إذا اختفت عملية التحكم أو تجاوز الحاجز خمس ثوانٍ. نجح اختبار فقد العملية فعليًا، واختبار انتهاء المهلة مع بقاء العملية حية. هذا لا يحمي من تعطل Docker أو المضيف نفسه، ولا يشغّل DB أو خدمات مشتركة.

### ترتيب الرجوع

بدء Core القديمة قبل اكتمال Web القديمة أظهر Access-Reject واحدًا لكلمة مرور صحيحة أثناء إعادة تهيئة مخطط الترخيص القديم. عدّل مشغل الرجوع المحلي لبدء Web أولًا، ثم انتظار صحتها وحالة الترخيص المتحقق منها، وبعدها بدء Core. حالتا فشل محاكاتان للجاهزية والترخيص أثبتتا منع بدء Core، مع استهلاك محاولة الرجوع وعدم تكرارها تلقائيًا.

الثمن هو نافذة توقف مصادقة أوضح أثناء الرجوع؛ هذه مفاضلة موثقة وليست رجوعًا بلا انقطاع.

المحاولة الأولى للتبديل تضمنت خطأ JSON في ملف تغيير وجهة المحاكي، لا رد RADIUS؛ جرى جعل نشر الوجهة ذريًا وإعادة الاختبار بنجاح. كذلك رفضت محاولة إعادة تجربة قبل أي تبديل بسبب علامة بدء باقية من الدورة الأولى؛ حفظت آثارها، وثبت عدم وقوع إجراء قبل تجهيز دورة الاختبار التالية. لا تخلط 127 طلبًا ناجحًا في هذه المحاولة المرفوضة بنتيجة تبديل فعلي. محفوظات الدورة الأولى تحت `first-cycle`، ورفض العلامة تحت `recheck-stale-marker-refused`.

## الترخيص

تحقق كود الصورتين ومفتاح الناشر المثبت فيهما من توقيع حزمة العميل الأصلية المحفوظة: التوقيع صحيح والمفتاح العام نفسه. رفض التحقق الكامل النسخة المحلية بسبب hardware_binding في النسختين، وهو المتوقع للمختبر. لم تُثبت حزمة العميل على جهاز جديد ولم تُتصل جهة الإنتاج.

نجحت ثماني حالات حزمة موقعة اصطناعية في كل إصدار: صحيحة، تلاعب، هوية جهاز أو منظومة خاطئة، انتهاء، غياب انتهاء، حد سالب وغياب توقيع؛ 16 حالة. ونجحت خمس حالات منع فعلية عبر RADIUS في كل إصدار عند إبطال lease أو انتهائها أو عدم تطابق package hash أو فقد صف الترخيص أو إلغاء الترخيص الاصطناعي؛ عشر حالات، مع عودة القبول بعد استعادة الحالة الاصطناعية الأصلية. **هذه ليست إثبات تفعيل ترخيص العميل الحي بعد التحديث.** يلزم قبوله لاحقًا على جهازه ضمن نافذة التنفيذ المصرح بها.

## الموارد وحدود النتيجة

سُجلت 117 عينة Docker stats في الجولة النهائية. الذروة المرصودة: DB نحو 723.8MiB، وWeb الجديدة 100.5MiB، وCore الجديدة 80.83MiB، وعملية التحضير 41.48MiB. ذروة CPU لـDB كانت 111.74% وفق عداد Docker الذي يسمح بتجاوز 100% لعدة أنوية. ليست هذه مقارنة سعة أو توقع RAM للعميل؛ الحاويات محدودة والحمل اصطناعي وقصير، والعينات بدأت أثناء الجولة ولا تمثل قياسًا مضمونًا لكل ذروة لحظية. لا استنتاج عن SSD العميل أو VPN أو ذاكرة المضيف.

تظل نتائج الجولة السابقة محفوظة: 26 اختبارًا ماليًا، مطابقة 394,937 صفًا أصليًا في 12 جدولًا، استعادة أصلية بحساب محدود، نسخ واستعادة 2.7.0، وتوافق الرجوع على DB الموسعة. لم يُعاد تشغيل العمليات المالية لمجرد هذه الإضافة؛ الصور والكود المترجم لم يتغيرا.

ظهرت في تهيئة 2.6.5 المختبرية أولًا حالة metadata cache لتريغر بعد الاستعادة: SHOW CREATE فشل، وCHECK TABLE سليم، وبصمة TRG قبل/بعد متطابقة؛ فتح الجدول مجددًا في النسخة المحلية أصلح القراءة. لا دليل ينسبها إلى 2.7.0 أو فساد ملف، ولم يضف إجراء FLUSH على العميل. عولج أيضًا سباق كتابة heartbeat داخل أداة المختبر بكتابة ذرية قبل الجولة النهائية.

## التسليم الآمن

الاختبارات المطلوبة محليًا مكتملة ضمن هذه الحدود. الخطة المقاسة قابلة للاستخدام أساسًا لتحديث يدوي **بنافذة صيانة وبقبول حي لاحق**، وليست تفويض تنفيذ أو ضمان صفر انقطاع. لا تستخدم الحارس القديم أو manifest المختبر على العميل؛ يلزم عند تفويض التنفيذ تثبيت هوية المضيف والملفات والصور الحالية، ونسخة حديثة، وmanifest جديد دون مفاتيح/تبديل ثقة المختبر. لا DBrestore تلقائية؛ الرجوع المختبر يعيد الزوج القديم على DB الحالية، ومرة واحدة قبل القبول وفي النافذة المحددة، مع التوقف والتصعيد عند الغموض.

قبول NAS والمحاسبة الطبيعية وترخيص الجهاز الحقيقي والتوجيه والأنفاق والتعافي بعد إعادة إقلاع مضيف العميل تبقى خارج المختبر. لم تُجر هذه الاختبارات الحية تنفيذًا لطلب المستخدم بعدم تحديثه. لم تُختبر الترقية الذاتية عبر لوحة العميل بهذه الجولة.
