## الوضع الحالي لكل مسار

### اللوحة الجديدة CONTROL_V2

- صفحة السيرفر الفعلية هي `https://control.max-net.net/#updates`، وليست واجهة محلية فقط.
- جرى تنظيف بيانات العرض الوهمية وتجهيز ملفات جاهزية النقل مع إبقاء الربط الخارجي معطلًا. غياب IP pools أو قوائم العملاء الحقيقية لا يعني أنها نُقلت ثم ضاعت؛ لم تُنقل إليها إدارة الإنتاج.
- خدمة ومفاتيح وقاعدة وجلسات مستقلة؛ Unix socket وHTTPS وCSRF وصلاحيات قائمة. تبقى شبكة الخدمة الصادرة وDocker والجدولة ومنفذات المضيف العامة معطلة.
- نُشرت قناة 4k الخاصة أولًا عبر API اللوحة، لا بضغط زر متصفح نيابة عن الإنسان. كان سجلها وصفحة `/pilot-updates` فعليين، لكن تبويب المركز الرئيسي ظل واجهة محاكاة؛ اعترفنا بهذا الحد وصححنا الربط والترميز في الصفحة الرئيسية وتحقق المتصفح منها.
- اكتمل ناشر الإصدارات الجديد: مسودات، ملاحظات، صور مثبتة، Web/Core، جمهور عام/دومين/محلية، هويات قراءة محمية، مراجعة وتأكيد الجمهور، توقيع، منع تكرار، سجل وأحداث، وسحب الإتاحة.
- لا يبني الناشر صور Docker ولا يفحص محتوى Registry فعليًا. لا يعني النشر وصولًا أو تثبيتًا، ولا تُعد هويات العرض المسجلة وصلات عملاء مؤكدة.
- عند التسليم: صفر إصدارات أو هويات أو أحداث جديدة على الإنتاج، وأرشيف تجربة 4k مكتمل ومحفوظ. نشرت شيفرة الناشر فقط؛ اختبارات الإصدار الاصطناعي ظلت داخل المختبر المحلي وأوقف خادمها.

### اللوحات القديمة والإنشاء

الإنسان قرر إبقاء إدارة التراخيص والمنظومات والأنفاق على اللوحات القديمة، وإبقاء V2 مستقلة مع استخدام مسار تحديثاتها. نقل الإدارة أو المحركات أو الترخيص لم ينفذ. خطة النقل (`../../max_saas_panel_v2_local/MIGRATION_PLAN.md`، مرجع عمل محلي خارج حزمة المستودع) محفوظة كمهمة مؤجلة، لا تفويض دائم.

في نسخة المصدر القديمة التي راجعناها: `central_provision.py` يجهز Web/Core/DB خاصة للمستأجر وربط المضيف، و`tenant_release.py` يسحب الصور المحددة في config، يثبتها بـRegistry digest، ويأخذ bootstrap schema من صورة Web المختارة. لم نقرأ قيمة إعداد اختيار الصور الحية في هذه الجولة؛ لا يقال إن اللوحة ستسحب latest حتمًا دون التحقق منها عند التفويض.

تحتاج النسخة الجديدة مستقبلًا إلى تجهيز قناة التحديث والثقة وهوية النسخة واعتمادها وربط منفذ المضيف أثناء الإنشاء. رفع صورة جديدة وحده لا يجهز هذه الأشياء. أي تغيير لمسار الإنشاء يقيد بالإنشاءات الجديدة ولا يعيد إنشاء الحاويات الحالية.

### نظام MAX والمحاسبة والترخيص والأنفاق

- المصادقة والمحاسبة الفعليتان لدى FreeRADIUS، وليستا نجاح Flask أو API. قبول المصادقة لا يثبت قيام جلسة، وACK لا يثبت Stop أو تسوية مالية.
- قاعدة الأعمال لكل منظومة مستقلة عن قواعد لوحة التحكم وخادم الترخيص. لا تستعد قاعدة قديمة فوق استخدام أحدث، ولا تجعل voucher_id فريدًا في المبيعات لأن التجديدات شرعية ومتعددة.
- في الاستضافة الحالية توجد خدمات خاصة وخدمات مشتركة. تحديث منظومة لا يجيز تبديل الأنفاق أو DB أو خدمات مستأجر آخر. يلزم التحقق من labels/التركيبات/الشبكات/صور فعلية قبل التنفيذ.
- توقيع صورة MAX، وتوقيع الترخيص، وتوقيع بيان تحديث control ثلاث ثقات مستقلة. لا تغير إحداها لتجاوز فشل الأخرى.
- سأل الإنسان عن مهلة 24 ساعة عند تعذر خادم الترخيص. لا يوجد في هذه المحادثة قبول مختبر يضمن هذه المدة لكل حالة. مدة العقد، وسياسة العمل دون اتصال، والـruntime lease، وحارس الوقت ليست شيئًا واحدًا؛ يلزم قراءة الكود والبيئة واختبار معزول عند طلب ذلك، دون تجاوز الإنفاذ.
- اقترح الإنسان نفقًا ثانيًا موازيًا قبل إلغاء الأول أثناء نقل مستقبلي. لم ينفذ هذا الاقتراح، ومسار الوصول الوحيد للعميل ما زال محميًا. لا تنشئ أو تلغِ نفقًا أو تغير NAT/routing/NAS من مجرد قراءة النقاش.

## ما يفتح بعد موافقة جديدة

الخطوة المقترحة التالية تجهيز مستهلك التحديث العام وربط إنشاءات اللوحة القديمة، واختباره معزولًا، ثم دومين تجريبي مفوض بصور ثابتة؛ تغييرlatestوالنشرخطوةلاحقةبعدالقبول. تطويرها لا يجيز نقل الترخيص أو إيقاف لوحات أو تحديثAS/4k/MAX. احصلعلىنطاقالخطوةالمطلوبةمنالإنسان،ولا تعِدطلب إذن لجزء سبق تفويضه داخل ذلك النطاق.

للاستئناف يكفي إرسال: **«اقرأ AGENTS وSESSION_RESUME وFULL_SYSTEM_HANDOVER ومرجع الوصول الخاص، ثم أخبرني بالحالة والمتبقي دون تنفيذ تغييرات.»** لا يحتاج الإنسان نسخ المحادثة أو إعادة إرسال بيانات الدخول ما دامت المراجع المحمية متاحة؛ إن فقد مرجع محدد يذكر اسمه وحده بدل طلب جميع التفاصيل من جديد.
