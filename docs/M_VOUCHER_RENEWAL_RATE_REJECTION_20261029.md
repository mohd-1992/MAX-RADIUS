## الخلل المحدد

`snap_rate_limit_str` فارغ نصيًا (`''`، الطول صفر) في كرت سياسته مجمدة بالفعل، وسرعتا الباقة صفر بمعنى غير محددة. Core الفعلي يحتوي شرط post-auth التالي: يقرأ `COALESCE(snap_rate_limit_str,'0/0')` ثم يرفض إذا كانت النتيجة فارغة. COALESCE يعالج NULL فقط، لذلك تبقى القيمة الفارغة ويصبح شرط الرفض صحيحًا. غياب حد السرعة هنا يحتاج التمثيل المعتمد `0/0` بدل فراغ يفهمه Core كفشل قراءة.

المسار المحلي المتصل بالملاحظة `services/quick_action_service.py::action_renew_package` يقرأ `SELECT * FROM wisp_packages` ثم يكتب `pkg.get('rate_limit_str') or ''` إلى snapshot. مخطط packages الحي لا يحتوي العمود rate_limit_str. هذا عيب في المسار، ولا يصح قصر العلاج الدائم على الباقات غير محددة السرعة؛ يجب توليد/حفظ سياسة السرعة الصحيحة للباقات المحددة والـburst أيضًا. تطابق توقيت التجديد ثم الرفض مع القيمة المخزنة يربط الحادث بهذا المسار، لكن لم تُنفذ إعادة تجديد أو مصادقة تشخيصية لإنتاج تتبع فرع الطلب.

المراجع: `docker/freeradius/license-capacity-postauth.conf`، و`database/schema_mysql.sql` لدالة تثبيت السياسة، و`core/rate_limit.py` و`core/radius_sync.py` لعقد السرعة. عدم ظهور سطر يخص الحساب في ذيل سجلات Core لا يثبت أن سبب الرفض سجل نصيًا؛ الدليل هنا بيانات حية وشرط Core المركب، لا debug أو تجربة طلب جديدة.
