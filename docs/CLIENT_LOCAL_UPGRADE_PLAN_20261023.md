## فحوص ما قبل التنفيذ — 25 أكتوبر 2026

**نطاق الحماية المعتمد لاحقًا:** استبعد الإنسان ضياع الجهاز وقرصه بالكامل. لا يطلب خادم احتياطي أو نسخ متزامن، ولا يجعل تفعيل binary log وإعادة تشغيل DB شرطًا لتحديث Web/Core. تبقى سلامة الترحيل والرجوع والتعافي من تعطل مفاجئ مع سلامة القرص؛ خطر commit=2 عند تعطل نظام التشغيل/الطاقة لم يلغَ بهذا الاستبعاد. تراجع مقترحات الاسترجاع الزمني الأوسع أدناه وفق هذا النطاق، ولا يفهم التوضيح إذنًا لتعديل العميل.

[فحوص الجاهزية الفعلية والنسخة الحديثة](CLIENT_AS_PREFLIGHT_20261025.md) مقبولة ضمن نطاقها دون تحديث: التوقيع وربط الترخيص والتصريح الحالي، ومطابقة NAS/SQL والمحاسبة الطبيعية، وثبات ملفات التشغيل؛ واستعادة اللقطة الجديدة في64 جدولًا و667354 صفًا مع تطابق كائنات القاعدة، وحزمة مشفرة متحقق فكها خارج العميل. لا تعاد الجولات المكتملة. هذه القراءة تخص الصور الحالية؛ قبول المرشح مع الترخيص وNAS الفعليين يبقى بعد تنفيذ مفوض.

الحفظ عند العميل مضبوط على commit2؛ اختبر التعافي المحلي في الجولة الختامية أعلاه ولم تغير إعدادات العميل. تعطيل log_bin يعني غياب طبقة الاسترجاع الزمني تلك، لكنه لا يمنع وحده التعافي الاعتيادي بواسطة InnoDB أو تحديث التطبيق. مهلة metadata الافتراضية86400 ثانية غير مناسبة لنافذة التصريح القصيرة؛ نجح اختبار مهلة جلسة ثلاث ثوانٍ والفشل الصريح قبل Core الجديدة. الصور غير محملة مسبقًا على العميل وفق آخر قراءة فعلية. التزام الإنسان يمنع الأسماء أثناء فترة الأمان، دون حاجز جديد مطبق. لا تبديل أو استئناف مراقبة مستنتج من قبول الفحوص.

## نتيجة المحاكاة المحلية — 25 أكتوبر 2026

[المحاكاة على صور العميل ولقطة بياناته](CLIENT_AS_UPGRADE_REHEARSAL_20261025.md) اجتازت ترحيل Web/Core واختبارات RADIUS وحفظ بياناته والنسخ والاستعادة. **الرجوع المباشر إلى 2.6.2 بعد تغيير اسم حساب غير آمن**: ثبت في كرت اصطناعي أن النسخة القديمة تجاهلت استهلاك الاسم السابق، وعادت القراءة الصحيحة بإعادة 2.6.5 دون استعادة DB. لذلك يلزم منع فعلي لعمليات تغيير الهوية والميزات الجديدة أثناء نافذة الرجوع، أو زوج رجوع متوافق مختبر؛ حفظ الصور القديمة وحده غير كافٍ. لم ينفذ حاجز أو تحديث على العميل.

المرجع المعتمد r2 أعاد اللقطة الأصلية بتوقيت MariaDB الصحيح Asia/Riyadh؛ احتفظت r1 بأدلة اختبار قفل metadata. نطاق الحاويات يبقى Web/Core، مع تهيئة مخطط منفصلة متوقفة عند أي فشل، وبقاء DB/L2TP/Autoheal. أزمنة المختبر ليست تعهدًا بزمن الانقطاع. قبول الترخيص الحقيقي وNAS الإنتاجي ما زال مطلوبًا عند تنفيذ مفوض لاحقًا؛ اختبارات المرور الإيجابية محلية بحالة ترخيص اصطناعية وRouterOS API محاكى. جميع حاويات المحاكاة موقوفة والأدلة محفوظة.

مراجعة 25 أكتوبر اللاحقة: [المقارنة الفعلية والاعتماد الحرج](CLIENT_AS_IMAGE_COMPARISON_20261025.md) تؤكد أن نطاق الحاويات Web/Core فقط، لكن radacct_owned ومخطط الملكية غير موجودين عند العميل. يلزم تجهيز المخطط واختبار الأقفال والرجوع قبل تفعيل Core الجديدة؛ لم تثبت ضرورة ترقية محرك MariaDB. L2TP مطابقة للمنشور، ولا احتياج وظيفي مثبت لتحديث Autoheal. يشير release.json إلى زوج أقدم من latest؛ لا يشغل المثبت العام لتحديث العميل. تتجاوز التفاصيل التوصية المبدئية أدناه.

عند استعمال ميزات تعديل المشترك والكرت، يلزم الزوج المختبر. لذلك ترتيب Web ثمCore في الجدول أدناه لا يمنح قبولًا نهائيًا لـWeb منفردة: يحدد المختبر أولًا توافق الفترة الانتقالية، وتبقى عمليات هذه الميزات خارج نافذة التبديل حتى اكتمال الزوج والتحقق. إذا لم يثبت التوافق الانتقالي، تستخدم نافذة واحدة قصيرة بخطوتين منسقتين وخطة رجوع للزوج، مع بقاءDB/L2TP دون تغيير. لا تشغّل نسختيWeb بعمالهما على قاعدة الإنتاج.

المتبقي قبل طلب التنفيذ: جرد التعديلات والمجلدات المرتبطة وطبقات الكتابة، تحقق هوية المضيف والترخيص وlease وموارد التخزين، نسخة حديثة متسقة واختبار استعادتها معزولًا، اختبار تهيئة المخطط والتريغرات وحفظ الحسابات والعقود والأرصدة والسجلات، قياس نافذة التبديل والرجوع، وتجهيز الصور مسبقًا. لم تنفذ هذه الأعمال على العميل ضمن قراءة الإصدار؛ لا وعد بصفر انقطاع ولا استعادةDBتاريخية فوق محاسبة جديدة.

الاقتراح العملي: تحديث Web/Core فقط بعد نجاح التجهيز، وتأجيلMariaDB/L2TP/Autoheal ما لم يثبت احتياج مستقل. يقبل التبديل بهوية الصور والتوقيع والترخيص وlease ثم مصادقة طبيعية وStart/Interim/Stop عند حدوثها ومقارنة العدادات، وليس healthy وحدها. أي فشل يوقف التوسع ويستدعي رجوعًا متوافقًا مع أحدث بيانات الإنتاج. ما يلي الخطة الأصلية المؤجلة بتاريخ23أكتوبر؛ وصف2.6.5 بأنهاWebفقط يخص مرشح ذلك اليوم ويستبدل للمرشح الجديد بالمراجعة أعلاه.

## الهدف والنطاق

تحديث المكونات المطلوبة على مراحل، مع تقليل توقف الخدمة وحفظ تصحيحات العميل وإمكانية الرجوع. آخر مرجع مقبول للعميل مؤرخ 22 أكتوبر 2026؛ لا يثبت حالته الحالية. صورته تتضمن تصحيحات خاصة به، ومنها معالجة النسخ إلى Telegram، فلا يستبدل محتواها بصورة أحدث قبل مقارنة الاعتماديات والسلوك.

[الإصدار 2.6.5](RELEASE_20261023_265.md) يغير Web فقط، وعروضه الحالية مقيدة بالدومينات m وmax1 وshn. تحديث العميل المحلي يحتاج مسارًا مثبتًا خاصًا به؛ لا تستخدم هوية أو عرض دومين له، ولا توسع الإتاحة العامة أو المحلية لبقية العملاء.

## الفحص والتجهيز قبل الانقطاع

1. تثبيت هوية جهاز العميل ومشروع Compose والحاويات الفعلية وبصمات الصور والمجلدات والتخزين ومنافذ NAS. تقارن الصور المرشحة بالحالية لتحديد الخدمات التي تحتاج تبديلًا فعلًا.
2. تحديد تصحيحات العميل التي يجب حفظها، ومراجعة توافق Web وCore والمخطط والتريغرات والترخيص ومسار التحديث المحلي. لا يعتمد رقم النسخة أو latest وحده لإثبات التوافق.
3. تجربة الصور المرشحة والتراجع على نسخة بيانات معزولة، بلا اتصال براوترات العميل أو تراخيص إنتاجه أو Telegram أو عماله الخارجيين. تشمل التجربة آثار التهيئة التلقائية عند بدء Web؛ حقل migration=none لا يكفي لنفيها.
4. تجهيز نسخة أمان حديثة ومتسقة ومشفرة لقاعدة البيانات والتخزين والإعدادات، والتحقق منها خارج الجهاز. تحفظ الصور والحاويات السابقة وطبقاتها القابلة للكتابة وملفات Compose والروابط الحالية.
5. تنزيل الصور مسبقًا وتثبيتها ببصمات محددة، مع قياس موارد الجهاز ووقت بدء المرشح والرجوع في المختبر. يجرى التنزيل والنسخ والخدمة تعمل، خارج نافذة التبديل قدر الإمكان. [تثبيت الصور بالبصمة في Docker](https://docs.docker.com/reference/cli/docker/image/pull/).

## ترتيب التحديث

| المكون | الإجراء المقترح | شرط القبول |
| --- | --- | --- |
| Web | تبديل منفصل أولًا بعد نجاح التجربة | توقيع وواجهة وترخيص وlease حديثة، مع حفظ بيانات العميل والتوافق |
| FreeRADIUS Core | خطوة مستقلة إن ثبت اختلاف مطلوب عن الإصدار المعتمد | مصادقة طبيعية ومحاسبة NAS وتقدم العدادات الفعلية بعد التبديل |
| MariaDB | نافذة مستقلة إن احتاج المحرك ترقية فعلية | تجربة ترقية ورجوع مدروسة تحفظ أحدث البيانات؛ لا رجوع ثنائي على مخزن غير متوافق |
| L2TP | تغيير مستقل عند الحاجة | بقاء أو عودة النفق الفعلي وإدارة العميل؛ يحمى مسار الوصول قبل تبديله |
| Autoheal | يراجع توافقه مع هوية الحاويات الجديدة | لا إجراءات متعارضة أو استهداف لحاويات قديمة أثناء التبديل |

تبقى DB وCore وL2TP تعمل أثناء خطوة Web. يمنع تشغيل نسختين كاملتين من Web بعمال الخلفية على قاعدة الإنتاج نفسها. تراجع سياسة Autoheal أثناء التبديل وتنسق بصورة محدودة بدل إيقاف جميع خدمات الجهاز.

مدة lease قصيرة في آلية التشغيل الحالية؛ يقاس المتبقي الفعلي قبل التبديل، ويجهز الرجوع بحيث لا تترك Web الجديدة متعثرة حتى انقضاء التصريح. استمرار Core وحده لا يضمن استمرار قبول دخول جديد إذا انتهت lease.

عند تبديل Core، تحدد نافذة هادئة وتراجع إعادة إرسال طلبات المصادقة والمحاسبة لدى NAS. لا يفصل المشتركون جماعيًا، ولا يدعى انعدام فقد الحزم من نجاح أمر Docker أو healthy.

## التحقق والرجوع

قبل التبديل تحفظ لقطة محددة لهويات الصفوف والعدادات والعقود والأرصدة والتريغرات، مع أعداد الجلسات ومطابقتها مع NAS. بعده يتحقق التوقيع والبصمة والواجهة والترخيص وlease، ثم مصادقات طبيعية وInterim وStop عند حدوثهما وتقدم العدادات دون تراجع أو ازدواج. لا تعاد عمليات مالية أو تجديدات لاختبار التحديث.

يشغّل مراقب تبديل محدد المدة ومستقل عن Web وSSH، لا مراقبة دورية مستأنفة. تحدد معايير فشل ومهلة قبول قبل التنفيذ ويختبر الرجوع. عند فشلها يعاد المكون السابق المتوافق مع أحدث البيانات، مع حفظ دليل المحاولة وعدم تكرار أوامر مجهولة النتيجة. لا تستعاد قاعدة تاريخية فوق محاسبة جديدة.

## الانقطاع المتوقع ونقطة الاستئناف

هدف خطوة Web توقف اللوحة لعشرات الثواني، ويثبت الزمن بالتجربة قبل تحديد النافذة. تحديث Core قد يوقف استقبال الطلبات لحظيًا، وترقية DB أو L2TP قد تحتاج انقطاعًا أطول منفصلًا؛ لا وعد بصفر انقطاع.

عند عودة الإنسان لهذه الخطة، يبدأ العمل بفحص الهوية والتوافق للقراءة ثم تجهيز نتيجة قابلة للمراجعة؛ لا تعاد مشغلات نشر أو نسخ أو اختبارات مالية من جولات قديمة. مرجعا التنفيذ [DEPLOYMENT](DEPLOYMENT.md) و[ENVIRONMENTS](ENVIRONMENTS.md)، والتحقق [TESTING](TESTING.md).
