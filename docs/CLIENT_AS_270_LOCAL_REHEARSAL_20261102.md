# محاكاة CLIENT_AS محليًا: 2.6.5 → 2.7.0 والرجوع

النتيجة: نجحت الحالات المحددة أدناه على نسخة العميل الحديثة وصوره المثبتة بالبصمة، داخل Docker المحلي فقط. لم يُحدّث العميل ولم تُشغّل أدوات التحديث أو الحارس القديمة عليه. هذه نتيجة محاكاة للمسار اليدوي، وليست قبولًا للمصادقة على الراوتر الفعلي أو للتحديث الذاتي عبر اللوحة.

جذر الأدلة المحمي: `PRIVATE/client270-rehearsal-20261102-r2/`، حيث PRIVATE هو الإحالة المحلية الموصوفة في ENVIRONMENTS. الجولة r1 تمهيدية على بيانات 25 أكتوبر، ولا تُستعمل أرقامها بدل هذه الجولة. محفوظات العميل وأسراره وملفات SQL وإعدادات Core خارج Git والصور.

المرشح المنشور هو `2.7.0-20261102-r1`. جرى استعمال الصور نفسها دون إعادة بناء أو تغيير latest. حاويتا L2TP وAutoheal خارج التحديث والمحاكاة التشغيلية للأنفاق؛ لم تُستبدلا على العميل.

وصلت اللقطة المتسقة الحديثة كاملة وتحققت بصمات مكوناتها الثلاثة: SQL حجمه 216,642,777 بايت قبل الضغط و56,622,807 بعده، إعدادات Core بحجم 1,273,344 بايت، وملفات التخزين بحجم 17,073,209 بايت. استغرقت تجهيزها في المصدر 4.21 ثانية؛ بطء النقل السابق كان عبر وصلة الاتصال. بيانات اللقطة الفعلية: 51,432 كرتًا، صفر مشترك، و317,794 سجل محاسبة. قراءة الجرد السابقة 317,788 ليست تعداد اللقطة المتسقة اللاحقة.

حُفظت خيارات DB: InnoDB 512MiB، وAria/key كلاهما 128MiB، وredo 64MiB، وcommit=2. مصدر العميل أربع وحدات CPU ونحو 6.6GiB RAM دون حدود حاويات. المختبر أربع وحدات CPU لكل حاوية رئيسية، وDB بحد 1.5GiB وWeb بحد 1GiB وCore بحد 512MiB. الشبكة داخلية بلا منافذ منشورة أو وصول إلى NAS أو جهة الترخيص الإنتاجية. هذه فروق مقصودة؛ أزمنة المختبر ليست وعدًا بزمن العميل ولا قياسًا مماثلًا لتخزينه أو نواته أو ذاكرته.

استخدمت جهة توقيع وترخيص اصطناعية مستقلة داخل الشبكة، مع توقيع ونبضات فعلية وتبديل الثقة في عملية الاختبار فقط. الصورة والناشر الإنتاجي لم يتغيرا. رُفع حد المديرين في الترخيص الاصطناعي إلى 100 لاستيعاب ممثلي الحالات المالية؛ لم يُصدر أو يعدّل ترخيص إنتاجي. لا تستنتج من هذا قبول ترخيص العميل الحقيقي أو حدوده على جهازه.

## الملفات والإعدادات

- نسخ إعدادات Core يحوي 250 ملفًا عاديًا، ولم يُفقد أي منها. في Core القديمة تطابق 248 ملفًا؛ تغير clients.conf وmods-available/sql بسبب عناوين واعتمادات المختبر. في الجديدة تطابق 244 ملفًا؛ الفروق الستة هي clients.conf وmods-available/sql وqueries.conf وlicense-capacity-postauth.conf وmods-available/detail وsites-available/default. ملفات SQL والسعة وdetail الخاصة بالإصدار الجديد احتُفظ بها، وdefault ناتج مدخل Core الأصلي. سياسة هوية المحاسبة المخصصة ضمن الملفات المحفوظة. الإيصال: CORE-CONFIG-COMPARISON.private.json.
- استُخدم Web مع storage وuploads المنسوخين. لم تُنسخ سجلات التشغيل والنسخ الاحتياطية والكاش وعمليات التصدير القديمة باعتبارها متطلبات تشغيل. الملفات الحساسة تبقى داخل المختبر المحمي.
- نجح تحليل ملفات Compose العشرة المحفوظة قراءةً فقط؛ الخدمات الخمس موجودة وصورتا Web/Core المحلولتان تطابقان الحالية.
- **اكتشاف مهم:** Compose المحلول لا يحدد مدخل Web الخارجي، بينما الحاوية الفعلية تبدأ بـ `/bin/sh /run/max-rollout-kit/web-gate.sh`. لذلك إعادة إنشاء Web من Compose وحده لا تعيد كل حالتها الفعلية. المصدر المعتمد في التنفيذ اللاحق هو تعريف الحاوية الفعلي مع مراجعة طبقات Compose، وليس `compose up` عامًا.
- اختُبر لاحقًا زوج Web بمدخل حاوية فعلي، ونسختي web-gate.sh وnormal_launch.py المطابقتين للملفات المحفوظة، والعمال الأصليين. بدء الاختبار الأول بعمال معطلين كان مخصصًا لقياس المخطط فقط؛ لا يُخلط باختبار التشغيل الأصلي اللاحق.
- لم يتصل المختبر بالراوتر. محاكاة Docker داخل Web تستخدم وكيل GET فقط مقيدًا بوسم الجولة؛ صلاحيات كتابة Docker على المضيف لم تُعط للتطبيق. CAP_NET_ADMIN، وسياسات إعادة التشغيل والفحص الصحي ومنافذ العميل محفوظة في عقد التنفيذ، لكن المختبر لا يثبت عمل التوجيه والأنفاق أو التعافي المشترك فعليًا.

## تدقيق البيانات والآثار المتوقعة

قورنت بصمات **394,937 سجلًا أصليًا في 12 جدول أعمال** على أعمدتها الأصلية، لا العدد وحده. بقيت مطابقة بعد التحديث وبعد الرجوع المحدد، قبل تشغيل العمال الدوريين. يشمل التدقيق الكروت والحزم والباقات والمبيعات والمديرين والفواتير والمعاملات والمحاسبة وتاريخها.

التدقيق المستقل لـ66 سجلًا تجريبيًا جديدًا عبر الرجوع لم يجد حذفًا أو تغيير رصيد أو كلمة مرور أو حصة. الفرق الوحيد عند بدء 2.6.5: ملء global_seq_id الذي كان NULL في ثلاثة كروت وخمسة مشتركين أضافها برنامج الاختبار مباشرة. القيم تحولت من NULL إلى أرقام موجبة؛ هذا تفسير اختلاف hash الأولي في wisp_vouchers/wisp_subscribers، وليس فقد عمليات مالية. الإيصال ROLLBACK-DERIVED-FIELDS.

بعد تشغيل العمال الأصليين في مختبر لا يصل إلى الراوتر، انتهت ثلاثة كروت وفق حالتها الزمنية، وأُغلقت 196 جلسة من اللقطة بسبب Watchdog-Autoheal-Timeout. قورنت بمرجع إضافي مستعاد مباشرة من SQL الخام دون تشغيل التطبيق: فروق الكروت في status/expire_reason فقط، وفروق المحاسبة في acctstoptime/acctterminatecause فقط؛ لم تتغير عداداتها. هذه آثار تشغيل **2.6.5 القديمة نفسها** على لقطة زمنية قديمة داخل المختبر، وليست دليلًا على خطأ ترقية أو على حالة راوتر العميل. لذلك لا يُدعى ثبات hash كامل بعد تشغيل العمال.

أما استعادة النسخة بالنظام فقد حافظت على الكروت الأصلية كاملة في التدقيق، وأغلقت الـ196 جلسة المفتوحة بعلامة Backup-Restored-Closed؛ العداد محفوظ. هذا سلوك الاستعادة لمنع جلسات حية منسوخة، وليس فقد استهلاك. بقيت الجداول الأصلية الأخرى ضمن التدقيق مطابقة. السجلات التجريبية المالية المستعادة لها فروق الأرقام التسلسلية المشتقة الثمانية نفسها. مبيعتا التفعيل اللتان ظهرتا لاحقًا تخصان كرتي UDP المصطنعين فقط؛ صفر مبيعات جديدة تخص كروت المصدر الأصلية في هذا التدقيق.

## الأعطال وخطة الرجوع المختبرة

سبع حالات بأفعال Docker حقيقية على الجولة المحلية فقط:

1. بصمة صورة خاطئة: رفض قبل أي تعديل.
2. نافذة منتهية: توقف دون إجراء.
3. DB متوقفة: hold دون رجوع للحاويات ودون استعادة DB؛ أعيد تشغيل DB المختبرية لاستكمال التجربة.
4. Web معطلة بعد علامة القبول: hold ومراجعة يدوية بدل الرجوع التلقائي.
5. فقد عملية التحكم المحلية مع Web متوقفة: حارس مستقل أكد الحالة بقراءتين ثم أعاد الزوج القديم مرة واحدة على DB الحالية، وعاد HTTP. هذا يحاكي فقد عملية التحكم؛ لم يُقطع SSH حقيقي ولم تُثبت خدمة systemd على العميل.
6. استدعاء ثانٍ للحارس: لم يكرر فعلًا ولم يغير إيصال المحاولة المستهلكة.
7. Core الجديدة متوقفة: ثبتت استجابة صحيحة قبلها، ثم غياب العملية وفشل طلب RADIUS صحيح بقراءتين؛ رجع الزوج القديم وعادت استجابة مصادقة صحيحة. لا DBrestore.

الحالات الست الأولى على guard-local-v1 المحفوظ؛ حالة Core على التوسعة المحلية اللاحقة. هذه برامج تجربة محلية مثبتة على معرفات ووسوم المختبر، وليست مثبتًا صالحًا للتشغيل على العميل. كذلك نجح **47/47 اختبار وحدة** لمنطق حزمة الرجوع المرشحة؛ هي اختبارات محاكاة منطق، وتُفصل عن حالات Docker الفعلية. لا تعني تغطية كل عطل مادي أو كل احتمال تزامن.

### خطة التنفيذ اللاحق

1. بعد تفويض جديد للتنفيذ: تثبيت هوية المضيف والمعرفات والصور والإعدادات الفعلية من جديد؛ أي اختلاف غير مفهوم يوقف التنفيذ. أخذ نسخة حديثة للبيانات والإعدادات والترخيص والتحقق من بصماتها. بيانات المختبر ليست بديلًا لآخر نسخة يوم التنفيذ.
2. إنشاء جولة مستقلة، والزوج العامل 2.6.5 هو هدف الرجوع. حزمة 25 أكتوبر تستهدف زوجًا أقدم، ونافذتها انتهت وحارسها معطل؛ لا تعاد تسليحها أو إعادة استعمال تفويضها.
3. فصل تهيئة المخطط عن تبديل Core. **مهلة المخطط القديمة 15 ثانية غير صالحة** قياسًا إلى 50.745 ثانية هنا. تُستخدم مهلة أقفال جلسة 3 ثوانٍ وفحص نجاح بنيوي صريح؛ لا تكفي رسالة بدء Flask أو HTTP200. نجاح Core قبل وبعد DDL مثبت؛ استمرارية حمل NAS أثناء أول DDL لم تُقَس، فلا وعد بانعدام أثرها. عند تعثر التهيئة لا يُستكمل التبديل أعمى.
4. حفظ القديم وصورته وطبقته وإعداداته، وترحيل Core بالاستثناءات الموثقة، وحفظ storage/uploads وهوية الترخيص ومدخل Web وملحقاته ومنافذه وCAP_NET_ADMIN وسياسات تشغيله. تبديل Web/Core وحدهما بتعريفات مقيدة، دون compose up عام ودون تحديث MariaDB/L2TP/Autoheal أو إعداد NAS.
5. قبول فعلي لاحق: ترخيص العميل الحقيقي ونبضة حديثة، ومصادقة طبيعية من الراوتر، وتقدم محاسبة وجلسات سليمة. تبقى تعديلات الهوية والحذف وتغييرات الأنفاق خارج نافذة التحقق الأولية؛ أي تغير هوية/عقد غير مدقق يمنع الرجوع الأعمى ويحتاج مراجعة أحدث البيانات.
6. قبل القبول فقط، يمكن إعداد رجوع واحد محدود بعد تأكيد عطل Web/Core وسلامة DB والهوية والتبعيات. بعد القبول يكون الرجوع بقرار يدوي ومراجعة العمليات الجديدة. أي فشل محاولة أو غموض أو فقد DB يوقف الإجراء؛ لا تكرار ولا استعادة تاريخية تلقائية.
7. الرجوع المعتاد يعيد الزوج القديم على **DB الحالية**. النسخة التاريخية مسار كارثة منفصل لأنها قد تسقط العمليات اللاحقة. ضبط ذاكرة DB اختياري منفصل؛ لا يحتاج صورة جديدة ولا يُفعّل ضمن هذا التحديث تلقائيًا.

النتيجة التشغيلية: نطاق صور هذا العميل **Web/Core فقط**، لكن التنفيذ يتضمن أيضًا ملفات التشغيل/الربط وتهيئة المخطط وخطة الرجوع. لا يكفي سحب صورتين ولا يصح بناء تعريف Web من Compose وحده. التحديث الذاتي عبر اللوحة لم يُعتمد بهذه الجولة.
