## نطاق القياس

المصدر الحالي مع بيئة Web للصورة `4b08e7504c09b0d062fbf80eadee276d337701d2c849053715793d4ec3313d02` المستخدمة في تجربة m.max-net.net. نُسخت لقطة الاختبار المحلية الموجودة إلى volume مستقل؛ الأصل مركب للقراءة فقط أثناء النسخ. اللقطة تحتوي **57,553 كرتًا و344,153 جلسة و28,289 سجل بيع**. جدول المشتركين العاديين فارغ؛ لذلك لا نعطي أرقام أداء فعلية لقائمة PPPoE كبيرة.

MariaDB10.11 محلية بحد2CPU و1792MiB وbuffer512MiB، وعامل القياس بحد2CPU و1GiB، شبكة داخلية بلا منافذ منشورة وبلا Docker socket. القياس بحساب SQL يملك SELECT/SHOW VIEW فقط على بيانات التطبيق، ولا يشغّل Flask أو عمال التطبيق أو المصادقة أو العمليات المالية. استُخدمت الدوال الخدمية الحالية، واستخراج AST محدد لمقاطع القراءة من المسارات التي يستلزم استيرادها تشغيل عمال. نطاق المالك المقاس هو الإدارة؛ عزل الموزعين ليس اختبار قبول في هذه الجولة.

كل زمن في الجدول وسيط3محاولات دون tracemalloc. «بارد» يعني كاش خيارات التطبيق فارغًا، **ولا يعني تفريغ كاش MariaDB/القرص**؛ «دافئ» يعني نفس الطلب ضمن مهلة الكاش. وقت SQL يتضمن استلام النتائج في العميل، وليس CPU قاعدة البيانات وحده. عدادات Handler عمليات قراءة من المحرك وليست عدد صفوف فريدة. لا يقارن الجدول نسختين: إنها قياسات النسخة الحالية وظروف الطلب المختلفة؛ لا توجد نسب تحسن جديدة قبل تنفيذ بديل واختباره.

## ما لا أوصي به الآن

- زيادة CPU/RAM أو عدد عمال Web قبل معالجة العمل المكرر؛ قد تكرر العمال والكاش وتزيد استهلاك الذاكرة وضغط DB.
- زيادة ذاكرة الجداول المؤقتة في DB: ليست ضمن النطاق، ونتائج التجربة السابقة كانت أبطأ5–6%.
- تغيير البحث الجزئي إلى بحث مطابق، أو إسقاط السجل القديم/تغيير معنى التقرير للحصول على رقم أسرع.
- إعادة معالجة quota/history/collector/VOUCHER_COUNTS التي أصلحناها بالفعل باعتبارها نقاطًا جديدة؛ توثيقها في [الإصلاحات الخمسة](SQL_CPU_FIXES_270_LOCAL_20261106.md).
- تعطيل أو نقل `sync_voucher_activations` من طلب الصفحة في هذه المرحلة: قد يحسن ذيل زمن الاستجابة، لكنه يمس التفعيل وسجل البيع، ويخرج عن شرط بقاء العمليات المالية والمصادقة كما هي. لم نشغّله أثناء الفحص.
- تخفيف احتياطات PDF أو القفل العام للعمليات الثقيلة أو زيادة التوازي بلا قياس؛ PDF مقبول حاليًا وقفل العمليات الثقيلة موجود بالفعل.

## حدود الإثبات والإغلاق

اكتملت42محاولة توقيت صحيحة، و6محاولات إضافية للمحلل/مقطع Excel، وتجربتا ذاكرة وتجربة تزامن كاش. القياسات مباشرة لخدمات/مقاطع SELECT محلية؛ ليست اختبارات متصفح أو خادم Web كامل أو حمل متزامن واقعي، ولا تشهد على الترخيص أو NAS أو المصادقة/المحاسبة/المال الفعلي. بعض الاستعلامات تقرأ views ثقيلة؛ وجودها في DB لا يعني اقتراح تغيير حاوية DB، فمصدر الاستدعاء والتحسين المستهدف Web.

أداة القياس الأولى لم تدعم context-manager لاتصال مساعد الرسم، فكانت قراءة ذلك الجزء غير مكتملة؛ **استُبعدت نتائج الدورة الأولية** وصُححت الأداة وأعيد قياسها في ملف TIMING. تجربة تجهيز Excel لجميع أجزاء حزمة كبيرة أوقفت محليًا بلا نتيجة مكتملة؛ استبدلت بقياس أول400كرت، ولا نستنتج منها زمن الحزمة الكامل. خطأ معاملات في أداة هذه التجربة استُبعد قبل المحاولات الثلاث النهائية. لا تُحسب أخطاء أدوات القياس أعطالًا في المنتج.

الزمن ليس نسبة إشغال CPU، والذروة المخصصة في Python ليست إجمالي RAM. لم يثبت تسرب ذاكرة أو ضغط حرج حي. لا نسب تحسن جديدة أو ضمان زمن قبل بناء البدائل ومقارنة نفس النتائج وحقوق الوصول واللقطات والتزامن والإلغاء والتنظيف. لا Core أو فهارس/مخطط DB مطلوبان لتنفيذ المقترحات في نطاقها المذكور؛ إن احتاج بديل ذلك يعاد تقييم نطاقه بدل تمريره ضمن Web.
