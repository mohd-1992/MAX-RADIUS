# تشخيص جذري لنمو الذاكرة — مختبر ديناميكي، 29 أكتوبر 2026

## النتيجة

لا يصح إسناد كامل زيادة RAM إلى جامع الاستهلاك والمبيعات. أثبت المختبر مساهمة تخصيص الذاكرة داخل MariaDB واحتفاظه بالذاكرة بعد الحمل، إضافة إلى أحجام الكاش، مع عبء SQL متكرر من الجامع والتقارير. حركة البيانات الطبيعية وحدها رفعت ذاكرة المحرك أيضًا. لم يثبت تسريب Python غير محدود، ولا أن زيادة المضيف التاريخية من نحو 48% إلى 56% ستتكرر يوميًا بالمقدار نفسه.

أقوى مقارنة سببية: نفس الصورة والبيانات وعدد الاستعلامات والقراءات والنتائج، مع تغيير إعداد تخصيص ذاكرة MariaDB فقط، خفضت RSS بعد الخمول من 536.78 إلى 385.51 MiB، أي 151.27 MiB أو 28.18%. هذا يثبت مساهمة طريقة تخصيص الذاكرة؛ لا يثبت أن جميع الذاكرة المحتجزة قابلة للتحرير فورًا أو أنها بلا فائدة.

## العزل وطريقة القياس

- استُخدمت صورة Web المنشورة المثبتة بالمعرف `sha256:c5ab9fe42359c867c6dedabaf607ff492b2652e8160fa5df987e34e645db098b` وصورة MariaDB `sha256:0d0945c57f75b3a3b9ebe71aedaaad005fa5305054e8fca3d2e42a8c92b43b5e`، دون إسقاط مصدر 2.7.0 عليها.
- بيانات اصطناعية: 100 ألف جلسة رئيسية و20 ألف سجل تاريخي، 20 ألف كرت و30 ألف عملية بيع عند البداية. ثم 21 دفعة تغير جلسات واستهلاكًا وكروتًا ومبيعات، موزعة على سبعة أيام منطقية، مع Interim وStop وتزامن مع الجمع والتقارير.
- انتهت الحالات المتحركة عند 137800 جلسة رئيسية و22100 كرت و32100 بيع، وإجمالي مبيعات 3210000، ورفع 11998060000 بايت وتنزيل 74980150000 بايت و3858 جلسة نشطة. تطابقت هذه المجاميع في المقارنات السببية.
- كل حالة لها DB/Web وتخزين مستقل، بحد 1 GiB و2 CPU لكل حاوية، وشبكة داخلية بلا منافذ منشورة. قياس الخمول 60 ثانية. لم يبدأ Flask أو عمال الإنتاج أو NAS؛ استدعيت وظائف الصورة المجمعة مباشرة على بيانات المختبر.
- قياسات التأكيد دون تتبع تخصيص Python، لتجنب احتفاظ أدوات القياس نفسها بالذاكرة. تجربة التتبع الاستكشافية منفصلة ولا تستخدم RSS الخاص بها لتقدير المنتج.

## نتائج المقارنات المكتملة

الجدول يقيس RSS لمحرك DB وPSS لعملية Python بعد الخمول، قبل أي إجراء تشخيصي لتحرير الذاكرة. MiB = 1048576 بايت. هذه ذاكرة عمليات، وليست نسبة استخدام المضيف أو كاش الملفات.

| الحالة | DB MiB | Python MiB |
|---|---:|---:|
| خمول دون حركة جديدة | 146.47 | 39.57 |
| حركة + جامع + تقارير، إعداد افتراضي | 536.78 | 51.24 |
| نفس الحمل مع `MALLOC_ARENA_MAX=2` للمحرك فقط | 385.51 | 52.48 |
| نفس الحمل مع Aria 16 MiB وkey buffer 8 MiB | 452.07 | 53.03 |
| حركة مع سجلات بيع تنتظر الربط | 344.17 | 39.44 |
| نفس الحالة مع تشغيل عامل ربط المبيعات | 369.78 | 39.63 |

في مقارنة الإعداد الافتراضي وarena والكاش تطابقت Questions=629600، وقراءات Handler_read_rnd_next=15180700، والجداول المؤقتة=371 ومنها 126 على القرص، وتطابقت المجاميع النهائية. لذلك فرق الذاكرة ليس نتيجة إسقاط بيانات أو تقليل عدد الاستعلامات في هاتين المعالجتين.

تقليل الكاش وحده وفر 84.71 MiB أو 15.78%. لا تجمع هذا الوفر مع وفر arena؛ لم تختبر المعالجتان معًا. أحجام InnoDB/Aria/key الافتراضية المرصودة 128 MiB لكل منها؛ حجم الحجز المنطقي لا يساوي بالضرورة RSS الفعلي.

عامل ربط المبيعات عالج 2100 سجل، وزاد DB بنحو 25.61 MiB وPython بنحو 0.19 MiB مقارنة بضابطه المطابق. له أثر، لكنه أصغر من أثر التقارير في هذه العينة.

## أين العبء في الكود؟

1. جامع الاستهلاك يعيد المرور على جلسات آخر 48 ساعة، بما فيها المغلقة حديثًا، ويحاول INSERT IGNORE ثم قفل checkpoint قبل اكتشاف عدم تغير العدادات. الصفحات محدودة وليست قائمة Python تتراكم بلا حد. القياس السابق على الإنتاج أثبت محاولات SQL متكررة؛ ليست كلها جلسات جديدة. في المختبر المتحرك أعلن الجامع مسح 240950 صفًا و91552 حالة changed خلال 21 دورة؛ changed وصف الخدمة وليس ضمان عدد الجلسات الجديدة.
2. صفحات التقارير تعيد تجميع التاريخ للمرشحات والفترات والأعلى استهلاكًا، بما ينتج قراءات وجداول مؤقتة. رسم المنحنى نفسه ليس وحده موضع التكلفة. هذا الحمل يرفع مستوى الذاكرة الذي يحتفظ به المحرك بعد انتهاء الاستعلامات.
3. حركة الجلسات والبيع المعتادة تسخن كاش المحرك وتوسع مساحات عمله حتى دون الجامع والتقارير؛ لذلك البيانات المتغيرة عامل حقيقي وليست فرضية مستبعدة.
4. لكل محرك مستقل كاش وتخصيصات خاصة؛ تكرار المحركات يزيد البصمة الأساسية على المضيف. عدد الاتصالات الأقصى ليس ذاكرة محجوزة كاملة مقدما لكل اتصال.

كتشخيص إضافي داخل DB معزولة فقط، استدعاء `malloc_trim` بعد الخمول حرر نحو 7 MiB من الحالة الافتراضية، مقابل نحو 49 MiB بعد ضبط arena. هذا يساند أثر توزيع التخصيصات والتجزؤ، ويمنع الوعد بأن أمر تفريغ واحد سيعيد كامل الفرق. لم يثبت هذا الاختبار أي صلاحية لتشغيل دالة تشخيصية داخل الإنتاج.

## النسخ الاحتياطي عبر مسار المنتج

اكتمل اختبار إضافي بنفس الحركة والجامع والتقارير، مع إنشاء سبع نسخ كاملة بواسطة `backup_service.create_backup` في الصورة الفعلية، دون إرسال إشعارات. استخدم SQL المؤقت والأرشيف تخزين لينكس داخل الحاوية؛ لم تُكتب النسخ على مجلد Windows المشترك. احتوت الأرشيفات عضو SQL غير فارغ: 50.39–62.42 MiB قبل الضغط، والأرشيفات 3.38–4.22 MiB. هذه ليست تجربة استعادة أو نسخة بحجم 100 MiB.

بلغ DB RSS بعد الخمول 527.88 MiB وPython PSS نحو 63.04 MiB، مقابل 536.78 و51.24 في حالة الحمل دون النسخ. لذلك لم يثبت أن النسخ السبع تضيف نموًا دائمًا فوق الحالة المقارنة؛ لا يعني الفرق السالب أن النسخ تقلل RAM. بلغ أقصى `memory.peak` لحاوية العامل 169.05 MiB شاملاً الأبناء والكاش، مقابل 86.08 MiB في نهاية الخمول قبل التشخيص؛ الكاش 23.51 MiB حينها. سُجلت ذروة anon نحو 80.29 MiB وfile نحو 82.56 MiB، وهما ذروتان منفصلتان لا تجمعان كعينة واحدة. لم يحدث OOM أو بلوغ حد الذاكرة في جولات التأكيد.

تطابقت مجاميع الجلسات والمبيعات والاستهلاك مع الحالة الافتراضية؛ سجلات النسخ والتدقيق الإضافية متوقعة داخل بيانات المختبر. انتهى مراقب cgroup المحلي، وتأكد خلو الحاويات والأحجام والشبكات الموسومة لكل جولة بعد التنظيف، وثبات هويات وحالات الحاويات المحلية السابقة. اختبار تفريغ SQL الأول منفصل وأقل تغطية؛ الحكم هنا من مسار النسخة الكاملة.

## الحدود والتوصيات

- الأيام السبعة منطقية مسرعة؛ ليست مراقبة متصلة أسبوعًا ولا تشغيل جامع كل دقيقة طوال أسبوع. لم يثبت تسريب غير محدود، ولم تُنفَ كل احتمالات النمو طويل المدى.
- مقارنة arena والكاش أجريت مرة لكل حالة؛ يلزم قبول أداء متكرر تحت حمل مماثل للإنتاج قبل اعتماد إعداد نهائي. اختلاف نظام المضيف وطوبولوجيا CPU يجعل الوفر المحلي غير قابل للضرب في عدد الدومينات كضمان.
- لا توجد سلسلة تخصيصات محفوظة وقت الزيادة التاريخية؛ لا يمكن توزيع كامل فرق RAM السابق بين الجامع والتقارير والكاش والـswap. حادثة تصدير Chromium السابقة سبب مستقل مثبت وليست هي الاختبار الحالي.
- الأولوية: تقليل إعادة معالجة checkpoints غير المتغيرة، وتقليل تجميع التاريخ المتكرر، ثم قبول ضبط المحرك/الكاش تحت حمل متزامن. تُقيّم مشاركة المحركات كخيار بنية مستقل، مع عزل قواعد العملاء وصلاحياتهم.
- لا توصية بإسقاط cache أو swapoff أو إعادة تشغيل عشوائية لتجميل النسبة. الأهم الذاكرة المتاحة وPSI وOOM واستمرار الخدمة، وليس RSS منفردًا.
- لم يتغير أي إنتاج أو ترخيص أو قناة أو صورة منشورة أو حدود ذاكرة. لم تستأنف المراقبة ولا العمل المتوقف على اللوحة و2.7.0. لم تختبر مصادقة ومحاسبة فعلية أو NAS في هذه الجولة.
