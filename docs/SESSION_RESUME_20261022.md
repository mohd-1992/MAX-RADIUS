سأل الإنسان عن إنشاء دومين جديد من **لوحة المنظومات القديمة**، وهل تجهز 2.6.3 على latest بدعم التحديثات. أوصينا بإصدار جديد مثل **2.6.4** مبني على2.6.3، لكن **لم نبدأ بناءه أو نرفع صوره أو نغير latest أو إعدادات الإنشاء أو ننشئ دومينًا**. آخر طلب بعد النقاش هو التوثيق والاستئناف، وليس تفويض تنفيذ الخطة.

المتبقي لتصبح النسخة مستهلكًا فعليًا للقناة الجديدة:

1. محدّث داخل Web يقرأ العقد الجديد ويتحقق من التوقيع وعرض الإتاحة والجمهور والصور، ويعرض الإشعار والتقدم والنتيجة.
2. منفذ مضيف محدد الملكية لتحديث Web/Core مع النسخ والترحيل والتحقق والتراجع دون DB restore تاريخية أو لمس الأنفاق المشتركة. لا تمنح Web وصول Docker عامًا لتجاوز controller.
3. تجهيز إنشاء الدومينات الجديدة من اللوحة القديمة بعنوان القناة والثقة وهوية التثبيت واعتمادها المحمي وربط المنفذ؛ لا اعتماد موحد داخل الصورة. صورة Core لا تحتاج إعادة بناء لمجرد إضافة استقبال التحديثات إلى Web، ما لم تتغير Core نفسها.
4. اختبار دومين جديد بصورة ثابتة أولًا: إنشاء، وصول إصدار موجه، تثبيت، تقدم، فشل وتراجع، وحجب عن غير الجمهور. بعد القبول فقط يراجع قرار تحديث latest للإصدار المختبر.

راجعت نسخة المصدر المحمية للوحة القديمة فقط في هذا النقاش: central_provision ينشئ Web/Core/DB مستقلات مع أنفاق مركزية مشتركة؛ tenant_release يسحب الصور المحددة في config، ثم يثبتها بـRegistry digest ويستخرج schema من Web. **قيمة config الفعلية الحية لا تثبت من نسخة المصدر**؛ قبل تنفيذ الإنشاء لاحقًا تحقق من إعداداته الحية بنطاق مصرح دون طباعة الأسرار.
