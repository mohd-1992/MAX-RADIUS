## السلوك

- مهلة المقبس لعميل مراقبة API خمس ثوانٍ، وسقف مشترك اثنتا عشرة ثانية للاتصال وتسجيل الدخول وقراءة الموارد والجلسات وإعادة المحاولة. يشمل السقف القراءات المتكررة للرد، ولا يشمل فحص الوصول السابق أو SQL أو قراءة حالة النفق.
- محاولة إضافية واحدة عند مهلة أو فشل اتصال مؤقت قبل اكتمال قراءة الموارد. لا تكرر رفض الاعتماد أو صلاحيات القراءة، ولا تعيد الجلب بعد قراءة موارد ناجحة إذا فشلت قراءة الجلسات اللاحقة.
- فحص الوصول يبقى 1.5 ثانية لكل محاولة في helper، مع محاولة ثانية عند الفشل. حالة النفق ليست إثبات نجاح API أو مصادقة RADIUS.
- تحديث التفاصيل بعد اكتمال الطلب السابق بعشر ثوانٍ؛ القائمة بعد اكتماله بثلاثين ثانية. التحديث اليدوي لا يبدأ طلبًا موازيًا، وحماية الخدمة تمنع فحص NAS متزامنًا داخل عامل الويب نفسه. الحماية ليست قفلًا موزعًا بين عمليات الويب.
- تميز الواجهة انتهاء المهلة ورفض الاتصال وفشل الدخول وتعذر قراءة البيانات. لا تصف كل فشل بأنه API غير مفعل. أزيل النص الافتراضي API مغلق من بيانات الإصدار.
- تحفظ آخر قياسات عتاد ناجحة في ذاكرة العامل والمتصفح مع وقت نجاح القراءة. عند فشل الموارد تعرض قياسات سابقة موسومة، ولا تعتبرها إثبات اتصال حالي. دون قراءة سابقة تعرض عدم توفر البيانات بدل نسبة صفر كقياس. الذاكرة مؤقتة ولا تستمر بعد إعادة تشغيل العامل/المتصفح.
- عدد الجلسات من المحاسبة مستقل عن قياسات العتاد؛ قراءة API الناجحة التي تعيد صفر جلسات تعرض صفرًا حقيقيًا بدل الرجوع تلقائيًا إلى عدد radacct القديم.
- أصلح تعريف KPI مكررًا في JavaScript للقائمة كان يسبب خطأ syntax ويعطل التحديث.

## التحقق وحدوده

نجحت 20 حالة معزولة تغطي المهلة الكلية، المقبس البطيء، إعادة المحاولة، رفض الاعتماد، فشل القراءة الجزئي، البيانات السابقة والتزامن، وثبات بروتوكول API العام المستخدم خارج المراقبة. نجح توليد القالبين ببيانات اصطناعية وفحص JavaScript الفعلي لعدم التداخل والاحتفاظ بالقياسات عند فشل API وHTTP.

نجحت ثلاث قراءات فعلية قصيرة لراوتر واحد على AS: زمن API نحو 11.36 و6.43 و3.19 ثانية، وفحص الوصول نحو 774 و1230 و227 مللي ثانية. القياسات من آلية وصول TCP/ICMP الحالية، وليست قياسات ICMP خالصة. كل قراءة أعادت موارد ناجحة دون بيانات سابقة. زمن الصفحة الكلي أطول من سقف API لأنه يتضمن فحوصًا وSQL إضافية.

هذه ليست جولة ضغط أو اختبار مصادقة/محاسبة RADIUS أو CoA/Accounting-Stop أو عمليات مالية. مهلات تلك المسارات لم تتغير؛ استمرار تفاوت API لا يكفي للحكم عليها. تفاصيل HTTP النهائية والأدلة الآمنة تُسجل في CURRENT_STATE، والقياسات الكاملة المحمية في المرجع الخاص.


فحوص HTTP الداخلية بجلسة إدارة موقعة لطلبات GET فقط أعادت 200 للقائمة والتفاصيل وملف JavaScript؛ هذا ليس اختبار إدخال كلمة المرور أو مرور المتصفح عبر الدومين الخارجي. فحص مسار الحالة النهائي على r2 أعاد وقت آخر نجاح وبيانات سابقة موسومة أثناء فحص متزامن، دون ادعاء نجاح API جديد. صححت r2 ربط نقطة الدخول بحماية التزامن والكاش الذي كشف فحص r1 غيابه؛ اختبار نقطة الدخول نفسه ضمن الحالات الثماني عشرة. حافظت الواجهة أيضًا على عدد المستخدمين أثناء حالة جارٍ الفحص.

القراءة النهائية عبر مسار HTTP للحالة على r2 أعادت 200، وAPI متصلًا، وقياسات جديدة غير موسومة كسابقة، دون خطأ ومع وقت آخر نجاح. بذلك تحقق مسار النجاح وحالة الفحص المتزامن على النسخة النهائية.

## تصحيح انحدار عرض الاتصال: r3

أبلغ المستخدم أن الراوتر يظهر غير متصل أحيانًا بعد r2. كشف التتبع تحويل نتيجة probe_pending ذات is_online غير المحسوم إلى غير متصل عند توليد القالب، وبقاء شارة التفاصيل الأولية دون تحديث عند التعافي. r3 يعرض جارٍ الفحص في هذه الحالة، ويحدث شارة الاتصال مع كل نتيجة مكتملة، ويستثني النتائج الجارية من كاش النتائج المكتملة. لا يغير فحص الوصول أو مهلات API/RADIUS/CoA ولا يخفي فشل وصول مؤكد. فحص طلبَي تفاصيل متزامنين على الويب الفعلي أعاد 200 وشارة جارٍ الفحص، دون عرض غير متصل للحالة الجارية. نجحت 20 حالة backend واختبارات HTML/JS لعرض pending والانقطاع والتعافي.
