# وقاية الوقت والإقلاع والطاقة — نتيجة محلية، 17 أكتوبر 2026

اكتمل المرشح المحلي والاختبارات المحددة. **لم يحدث اتصال بالعميل أو تعديل بياناته أو ساعته أو خدماته، ولم يُنشر Git أو صورة Docker.** لا يعني هذا اعتماد نشر أو ضمان انعدام الانقطاع. المراقبة الدورية السابقة تبقى موقوفة.

## مرجع الوقت والمناطق الزمنية

`core/time_service.py` أصبح يأخذ Unix epoch من ساعة المضيف فقط. أزيل جمع فرق NTP داخل التطبيق، بما فيه فرق قديم مخزن مثل ±10743 ثانية. عميل NTP في اللوحة فحص مطابقة فقط: النجاح يعني فرقًا محدودًا بحد ثانيتين، وليس إثبات حالة kernel NTP أو تعديل الساعة. فرق كبير أو استجابة غير محدودة/فشل أو فحص أقدم من ساعتين لا يعرض مطابقة حديثة. ضبط ساعة المضيف مسؤولية خدمة NTP في نظام التشغيل.

تخزين MariaDB وFreeRADIUS ما زال +03:00 كما هو؛ لا إعادة كتابة لتواريخ العقود أو الصلاحيات أو الاستهلاك. تتغير طريقة عرض اللحظة نفسها حسب منطقة IANA وبيانات tzdata المضافة كاعتماد صريح. اختبرت UTC وعدن ودبي وكاتماندو ونيويورك والقاهرة وLord Howe وKiritimati وPago Pago، والانتقال الصيفي والساعة المكررة. نقص بيانات المناطق في Python المحلي ظهر في أول اختبار، ثم عولج الاعتماد وأعيدت الحالات بنجاح؛ الأدلة الأولى محفوظة.

ساعة صفحة الإعدادات تعتمد timestamp من API الخادم وتقدمًا monotonic في المتصفح، بدل ساعة جهاز المستخدم أو خلط يوم UTC بوقت متصفحه. تحدث المرساة كل دقيقة وعند العودة للصفحة؛ تعرض عدم توفر الوقت إذا فشل القياس أو تقادمت المرساة، ولا تطبق فرق NTP. مسار الفحص لا يعيد جدولة النسخ الاحتياطي. لم تتغير بنية التصميم أو الثيمات.

**دقة النطاق:** إعداد المنطقة الحالي يستعمل أيضًا تقويمًا محليًا لجدولة النسخ/التقارير والقواعد، كما يوجد أمر صريح مستقل لضبط ساعة الراوتر. لم يُنفذ أمر الراوتر ولم نغيّر جداول المهام. إذن عميل NTP داخلي تشخيصي فقط، لكن لم نفصل حقل منطقة العرض عن تقويم الجدولة الموجود. لا يؤثر تغيير المنطقة في epoch أو حصة الكرت/صلاحية العقد؛ هذه الجولة ليست تدقيقًا شاملًا لكل تقرير أو دورة تقويمية عند DST. التواريخ اليومية/الجداول المحلية تختلف مشروعًا باختلاف المنطقة.

## حاجز الإقلاع

المرشح `deploy/clock-guard` ينتظر علامة systemd-timesyncd موثوقة وNTPSynchronized=yes وقراءتين مستقرتين بفاصل ثانيتين. يقارن الزمن الجداري بـmonotonic ويرفض نافذة تعرضت لقفزة. مهلة كل محاولة180ثانية ثم رفض بدء Docker، ولا يوجد فتح تلقائي بوقت غير موثوق. لا يوقف Docker القائم عند فقد NTP لاحقًا.

ينطبق على Docker المضيف كله؛ يجب أن يكون مضيفًا مخصصًا وأن تعمل الشبكة وNTP **خارج Docker/نفقه** لتجنب اعتماد دائري. لا يعتمد هذا adapter مع chrony دون تغيير واختبار. لا يمنع قفزة لاحقة بفعل مدير أو hypervisor؛ توحيد مالك مزامنة الساعة وتجنب تعدد أدوات ضبطها وضبط RTC/بطاريته تدابير مستقلة.

تجهيز الملفات ينشر ملفًا كاملًا حصريًا مع fsync للملف والمجلد، ويحتفظ journal وبصمات. اختبر تعثر الكتابة والتنافس وموت العملية وسط التجهيز/الأرشفة والاستئناف ورفض ملفات أحدث. هذا تراجع **staged-not-activated** فقط. عند تحميل drop-in فعليًا يلزم تعطيله أولًا وإبقاء helper حتى daemon-reload وتحقق التعريف المحمل، ثم أرشفة helper. لم يُنفذ/يختبر هذا المسار النشط، ولا يجوز استعمال التراجع المرحلي مكانه.

## قاعدة البيانات وانقطاع الطاقة

ملف `power-safe.override.example.yml` مثال اختياري غير مطبق، يشدد innodb-flush-log-at-trx-commit=1 وdoublewrite=ON وsync-binlog=1 دون تشغيل binlog. يزيد stop_grace_period وبدء healthcheck إلى120ثانية ويستثني DB من autoheal حتى لا تقتل أثناء recovery. المقابل: DB معلقة لكنها حية تحتاج تنبيهًا وتدخلًا بدل إعادة تشغيل متكررة. لا تُغير هذه الجولة Compose الأساسي؛ المصدر الحالي يطلب flush=2، ولم تُقرأ القيمة الفعلية لدى العميل هنا.

في المختبر نجحت استعادة واحدة نظيفة وأربع SIGKILL لعملية DB، وحفظ commits السابقة ورفض المعاملة غير المكتملة، بلا مبيعات مكررة، مع CHECK TABLE للجداول المستهدفة ثم مصادقة وStop حقيقي داخل DB الاختبار. وسيط زمن استعادة اتصال المختبر1.050ث، وأقصاه1.113ث؛ هذه أرقام fixture صغير وليست مهلة مضمونة للعميل.

قياس30commit لكل وضع: وسيط flush=1 بلغ5.265ms مقابل2.301ms للوضع2. وسيط13مصادقة لكل وضع12.684ms مقابل6.118ms. عينة محلية صغيرة تتأثر بالقرص والتحميل؛ لا وعد بصفر تأخير. تقوية durability أفضل ضد فقد commit حديث، لكنها ليست ضمانًا ضد عطل القرص أو controller/cache غير الآمن أو تلف filesystem. SIGKILL يبقي cache نظام التشغيل، ولا يحاكي انقطاع الطاقة الحقيقي.

قد يبقى NAS يعمل أثناء توقف الخادم؛ عندئذ تتعطل الطلبات مؤقتًا وقد يتأخر/يفوت Interim أوStop وفق retry/buffering الفعلي. لم نختبر سلوك راوتر العميل تحت انقطاع طاقة، ولا نختلق محاسبة أو Stop لتعويض نقص الدليل.

## ملفات أخرى ومخاطر باقية

- إنشاء مفتاح هوية الترخيص الأول يكتب ملفًا مباشرة؛ قطع الكتابة قد يترك PEM ناقصًا. اختبار المفتاح الناقص أثبت رفضه وعدم تدويره أو الكتابة فوقه. تقوية النشر الذري لأول إنشاء ونسخة آمنة من نفس المفتاح تحسين مستقل؛ لم نغيّر مفاتيح أو توقيعات.
- رفع خلفية كرت أو إنشاء archive أثناء انقطاع قد يترك ملفًا جزئيًا. الملف الموجود وحده ليس دليل نسخة سليمة؛ يلزم اكتمال/hash وفك تشفير وتجربة استعادة. حماية ملفات الحاجز الجديدة لا تعني حماية كل ملفات التطبيق تلقائيًا.
- كتابة إعدادات أو تحديث مبتور، قرص ممتلئ/تالف أو ضعف مصدر الكهرباء تبقى مخاطر. الأفضل UPS للمضيف والشبكة، تخزين موثوق وPLP إن توفر، مراقبة مساحة/صحة القرص، نسخ مشفرة خارج المضيف واختبار استعادة دوري. لا تفعيل تلقائي لـinnodb_force_recovery أو استعادة DB قديمة فوق محاسبة أحدث.
- Compose health order أثناء up ليس إثبات ترتيب كل حاوية بعد إعادة تشغيل daemon. حاجز الوقت وحده لا يثبت جاهزية DB/Core/Web. فحص Core الحالي المرتبط برد مصادقة قد يخلط رفض الترخيص المشروع بالصحة؛ فصل liveness عن readiness والتحقق التجاري مهمة مستقلة، وليس عطل عميل جديدًا مثبتًا.
