# التطوير المحلي وتسليم المهمة
1. افتح جذر Git الصحيح، وافحص `git status --short`؛ لا تعيد ضبط تغييرات الآخرين.
2. اقرأ [PROJECT_MAP](PROJECT_MAP.md)، وابحث عن اسم الخدمة/المسار: `python scripts/project_tools.py find action_add_quota`.
3. اقرأ القاعدة الخاصة بالمجال ثم نقاط الدخول والخدمة والمخطط/القالب المتأثر. تابع البحث خارجها فقط إذا أثبتت الاستدعاءات الحاجة.
4. نفذ أصغر تغيير يغطي السيناريو، مع توافق المدير ولوحة المشترك والعقود السابقة.
5. شغّل الاختبارات المختارة وفحوص الروابط والفهرس، وحدّث المستند المتأثر وبيانات الحالة عند التحقق.

## الإعداد
Python 3.11 هو أساس Dockerfile الحالي. التبعيات في `requirements.txt`؛ استخدم بيئة افتراضية مستقلة. يوجد `.env.example` و`env.example`؛ بعض القيم defaults فعلية وليست placeholders فقط، ولا تستخدم كاعتماد إنتاج. راجع [SECURITY_REVIEW](SECURITY_REVIEW.md). تحميل `.env` يختلف بين Compose وتشغيل Python مباشرة، فراجع `entrypoint.sh` والإعدادات بدل افتراض قراءته تلقائيًا.

`docker-compose.yml` يحتوي قيم تطوير افتراضية ومنافذ ثابتة؛ لا تشغله بجانب حاويات قائمة دون مراجعة التعارض. لا تشغل `python run.py` على قاعدة عميل لمجرد فحص الاستيراد؛ التشغيل يبدأ عمالًا وتهيئة. المثال الآمن الأول: `python scripts/project_tools.py doctor` دون اتصال حي.

أدوات المساعدة لا تستورد التطبيق ولا تتصل بقاعدة أو VPS. `check-python` تحليل syntax دون إنشاء التطبيق، و`check-docs` يفحص روابط الملفات، و`test-plan` يبين مجموعة الفحص. أوامر البناء في `build-plan` خطة فقط، لا تنفذ نشرًا.

التسليم يوضح: التغيير وسببه، الملفات، ما تم اختباره فعلًا، ما لم يُختبر، الإصدار/الصورة عند وجود نشر، والمخاطر المثبتة. لا تستخدم وثيقة CURRENT_STATE كبديل لقراءة حالة حية عند طلب المستخدم ذلك.
