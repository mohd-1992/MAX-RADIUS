# النتيجة النهائية لاختبار VMware — 17 أكتوبر 2026

**اجتاز حاجز وقت الإقلاع واختبار التعافي بعد Power Off الفحوص المحددة على سيرفر التجارب. لم يُعدّل نظام العميل أو بياناته، ولم تُنشر صور أو ملفات إصدار عامة.** الاختبار لا يثبت انعدام كل مخاطر الكهرباء أو جاهزية المصادقة لحظة ظهور healthy.

## النسخة والنطاق

قبل الاختبار طابقت قراءة فعلية صور الخدمات الخمس و171بصمة ملف تشغيل Web بين العميل وLAB. وبعد الإطفاء بقيت هويات الحاويات الأصلية الخمس وصورها وبصمات الملفات نفسها؛ لم نعاود الاتصال بالعميل لهذا التحقق اللاحق. بيانات الاختبار معزولة ومجهّلة من المختبر السابق، ولا نسخ لقاعدة العميل أو حساباته إلى هذه الجولة.

نُفذ حاجز Docker على مضيف التجارب فقط، مع بقاء صور R12 نفسها كخط أساس. **تعديل توحيد مرجع الوقت وواجهة الساعة في المصدر المحلي لم يُبنَ أو يُنشر داخل صورة Web في هذه الجولة.** اختبارات المصدر السابقة لذلك التعديل منفصلة في [BOOT_POWER_RESILIENCE](BOOT_POWER_RESILIENCE.md).

حُفظت نسخة DB/storage/config للتجارب مشفرة، ونُقلت وفُك تشفيرها وتحقق اكتمال الأرشيف وملف SQL خارجVM. مفتاح الفك لم يُنقل إلى السيرفر. لم نحتج لاستعادة قاعدة، ولم ننفذ اختبار استعادة كامل لهذه النسخة بعينها.

## البيانات والمصادقة والمحاسبة

قاعدة الاختبار وحاويتا RADIUS والمسبار منفصلة عن قاعدة النظام الأصلية. استعملت صور DB/Core/Web الفعلية المطابقة للعميل، مع تهيئة اختبار وleaseSQLمصطنعة محدودة في هذه القاعدة وحدها. لا تعديل للترخيص أو lease الأصلية يدويًا، ولا راوتر أو NAS حقيقي ضمن تبادل الحزم.

قبل القطع كان الشاهد خارجVMقد حفظ إقرار285معاملة تخزين مصطنعة في جدول المبيعات. بعد العودة تحققت كل الصفوف حتى آخر إقرار، وليس الصف الأخير فقط، وبقيت دون فقد أو تكرار ضمن المجال المحدد. المعاملة المفتوحة غيرالمعتمدة اختفت بعد recovery كما ينبغي. هذه معاملات SQL اختبارية؛ ليست إعادة تشغيل لجميع مسارات الدفع والمحفظة والتجديد في المنتج.

الزيادة تشمل مرورًا لاحقًا لم يكن ضمن آخر إيصال خارجي؛ الضمان المقاس هنا يقتصر على الصفوف والعدادات التي لدينا إقرار بها. لم تتناقص العدادات. أُرسلت حزمةStopحقيقية من المسبار للجلسة المصطنعة وتحققنا منacctstoptimeفيSQL. ثم نجحت مصادقة جديدة وStart/Interim/Stopمكرر، وخمس استجابات UDP متحقق التوقيع مع صف وعدادات نهائية صحيحة. لا نعتمد Accounting-Response وحدها دليل إغلاق.

اختبرنا إعدادflush=1 وdoublewrite=ON وsync-binlog=1 علىDBالاختبار، **ولم نغيّر إعدادات حفظ قاعدة النظام الأصلية**. لذلك لا تنسب تحمل commits المقاس إلى كل تثبيت يستخدم إعدادًا آخر مثلflush=2.

## السلامة والسجلات

نجح CHECK TABLE لستة جداول أساسية في قاعدة LAB الأصلية: radacct وradpostauth والكروت والمبيعات والمشتركين والترخيص، ولخمسة جداول فيfixture. أظهرت سجلات قاعدتي البيانات تنفيذ crash recovery ثم الجاهزية، دون مؤشرات فساد مقاسة. لم تظهر ERROR/Traceback/panic جديدة في سجلات Web/Core/DB الأصلية المحدودة بهذا الإقلاع.

ظهرت12سطرERRORفي RADIUSالمختبري أثناء بدء اتصالات SQLقبل جاهزية DB، ثم تعافى ونجح البروتوكول والتحقق. هذا عد للأسطر وليس12حادثة مستقلة. إعداد دخول هذه الحاوية الاختبارية يختلف عن مشغّل Core الأصلي؛ لم تظهر هذه الأخطاء في Core الأصلي. كما حُفظت أخطاء إعداد المشغّل السابقة قبل الاختبار (temp-server/استيراد fixture/DNS) ولا تُنسب إلى العميل أو تُحذف من الأدلة.

بصمات171ملف تشغيل بقيت مطابقة بعد القطع. لا يثبت ذلك فحص كل upload أو backup أو قطاع قرص. لم يقطع التيار عن مضيفVMwareوقرصه فعليًا؛ Power Offيحاكي تعثر الضيف مع بقاء طبقات تخزين المضيف حية، فلا توجد ضمانة عامة ضد فساد كل العتاد أو فقد cache عند كهرباء حقيقية.
