## المطلوب بحسب الأولوية

### P0 — مشترك: حارس وقت مرتبط بالـlease

الـlease الموقعة المنشورة في DB عمرها90ث عند التجديد الناجح، بينما `wait_ready` ينتظر150ث؛ مصدر المضيف ينتظر60 محاولة بفاصل2ث، أي120ث حتى لو كانت المحاولات فورية. واستهلاك المحاولة قد يجعل المدة تتجاوز الموعد الخارجي، كما أثبت اختبار244ث.

هذا **خطر مشروط بتوقف تجديد lease أثناء فشل Web**، وليس إثبات انقطاع مصادقة وقع بالفعل. بقاء Core شغالة لا يمنع رفض المصادقة عند انقضاء العقد. يلزم قياس الوقت المتبقي فعليًا قبل التحويل، وحجز وقت مجرّب لإقلاع Web السابقة وتجديد عقدها والتحقق منه، وموعد نهائي عام يشمل كل طلبات Docker/HTTP/exec، ورفض بدء التبديل إن لم تكفِ الميزانية. لا حل بتمديد الترخيص شكليًا أو تعطيل التحقق. تُجهز الصورة مسبقًا وتفحص الإعدادات قبل الإيقاف.

المستهدف: منفذ/حارس القناة للعميل وكود مضيف max-r؛ لا يستلزم تغيير صورة Core أو DB.

### P0 — المضيف: سجل تعافٍ قبل أول أثر

في `Runtime.update` تسبق أوامر stop/disconnect/rename/update وحفظ binding كتلة try التي تحمي إنشاء المرشحة. عند حقن فشل disconnect أو rename أو restart policy، بقيت Web القديمة متوقفة ولم يوجد previous_web محفوظ أو تحقق رجوع. هذا يثبت قصور مسار runtime المختبر؛ لا يثبت ما سيفعله مشرف خارجي غير ممثل في المختبر.

يلزم journal دائم قبل stop، وتسجيل كل أثر بهوية الحاوية، وتعافٍ مستقل عند انقطاع العامل أو ضياع الرد، وتحقق آمن من الحالة قبل التكرار. ينبغي أن يغطي التعافي جميع مراحل التبديل، لا فشل المرشحة فقط. سجل الصف unknown يمنع إعادة الطلب العمياء لكنه لا يعيد الخدمة بذاته.

المستهدف: خدمة مضيف max-r/منفذ التحديث، وليس صفحات Web أو Core/DB.

### P0 — قبول يحمي المصادقة والمحاسبة

فحص المضيف الحالي يفحص HTTP200 وvalid/version. لا يفحص في هذه الدالة وحدها fresh lease مرتبطة ببصمة العقد الحالية وCore، ولا checkpoint للمحاسبة. المنفذ المحلي لديه فحص أوسع، لكن توقيته يحتاج الإصلاح أعلاه. يلزم قبول وربط الترخيص والتوجيه وهوية Core وUID والعدادات المتقدمة دون تصفير أو إعادة محاسبة، ومراقبة حركة طبيعية عند وجودها. HTTP أو كون الحاوية running لا يكفيان. غياب حركة جديدة ليس عطلًا تلقائيًا.

### P1 — العميل: تهيئة قناته دون استعارة هوية max1

يلزم قارئ Local مستقل، الثقة والاستهداف وختم المخطط، ومنفذ محدود ومقبسه، وتوثيق Compose الدائم. تحفظ ملفات native-kit/control-new/override وبيئة التشغيل وحدود الموارد. لا تشغيل لحراس الجولات السابقة. اختبار بناء التعريف السابق حافظ mounts/entrypoint/command/env/IP؛ تجربة Docker الحالية اختبرت دورة الحياة، وليست نسخة تشغيل كاملة من إعدادات العميل الخاصة.

### P1 — m: قبول كتالوج وضبط بناء الحاوية

الكتالوج الحالي لا يحتوي2.7.1 ويختلف Core فيه عن العاملة؛ رفض إصدار غير مسجل نجح محليًا دون آثار. يعتمد انتقال Web ef615 مع نفس Core6e71، وقارئ خاص بالمستأجر، بعد اختبار توافق الرجوع إلى513d. لا تعيين rollback_compatible لمجرد تجاوز الرفض.

الدالة الحالية تعيد بناء Web من افتراضات ثابتة ولا تحفظ mounts إلى `/run/max-rollout-kit` و`/run/max-rollout-control` أو entrypoint المخصص. يلزم تعريف تشغيل مقبول يحدد بوضوح أي تبعيات تحفظ وأيها أصبحت غير لازمة في المرشحة، مع اختبار التوقيت وSQL والحدود والمقبس والتخزين. لا يُنسخ منفذ Compose لأن المستأجر لا يملك مشروع Web/Core/DB نفسه.

### P1 — اعتماد البيانات قبل الإرسال

نجح حفظ البيانات الاصطناعية وعدادات64bit والسجل المالي اللاحق لحد النسخ، دون DB restore. لم تختبر هذه الجولة محرك إنشاء النسخة نفسه أو استعادة آخر نسخة كاملة للعميل أو ترحيل جميع جداول عمله أو رجوع Web2.7.0 بعد تنفيذ مهام2.7.1 وكتاباتها الفعلية. اختبارات2.7.1 الوظيفية السابقة لا تستبدل اختبار انتقال/رجوع بهذه الظروف. يلزم اختبار محلي مكمل على اللقطة المتاحة، مع تثبيت التوقيع وتجديد lease والقبول الفعلي؛ دون مصادقة أو عمليات مالية على الإنتاج لغرض التجربة.

- **حفظ Core وDB وعدم استعادة بيانات قديمة:** دليل إيجابي محدود من دورة حياة Docker والبيانات الاصطناعية، وليس ضمانًا لكل بيانات العميل أو NAS.

- **استمرار الخدمة عند فشل Web/الترخيص:** غير معتمد بسبب مهلة lease والتعافي المبكر للمضيف. هذا مانع إرسال على منظومات نشطة حتى إغلاقه وإعادة الاختبار.
- **النشر الحالي:** لم يحدث؛ تظل المراقبة موقوفة.

النطاق المخطط تحديثه Web2.7.1 ومتحكم/منفذ التحديث الموافق لكل بيئة. لا تغيير صور Core/DB/L2TP/Autoheal، ولا إعدادات باقات أو NAS أو أرصدة. جداول الأتمتة الإضافية ضمن ترحيل Web المقبول، ولا تعني تبديل حاوية قاعدة البيانات.
