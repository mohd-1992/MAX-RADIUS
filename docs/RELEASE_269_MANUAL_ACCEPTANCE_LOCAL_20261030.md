## خلل Accounting-On المؤكد

التقط المختبر حزمة فعلية `Acct-Status-Type=7` عند أول استخدام PPP، ثم أثبت SQL والراوتر معًا: أُغلق سجل Hotspot بسبب `NAS-Reboot` بينما ظلت جلسته نفسها متصلة على NAS. الفارق بين الحزمة وإغلاق SQL نحو 0.848 ثانية. حدثت الحالة مع Core غير المعدلة:

`sha256:bc4d4644108018c7f67188e639bfeea9a4d12deedc01602bc15e219406ac4932`.

الاستعلام الفعلي المركب يطبق الإغلاق الجماعي على السجلات المفتوحة حسب `nasipaddress` ووقت البدء، دون نطاق خدمة Hotspot/PPP. النظير المصدري في [queries.conf](../docker/freeradius/queries.conf)، قرب السطر364. لم يثبت هذا الخلل بسبب وحدات Web الجديدة؛ Core لم تتغير. كما لا يكفي تخصيص اسم خدمة على نحو تخميني لأن Accounting-On قد لا يوفر تمييزًا صالحًا لإغلاق كل جلسة.

الأثر المحتمل: عدم تطابق عداد المتصلين وSQL مع الراوتر والتسوية/حدود الجلسات عند تهيئة أو إعادة بدء خدمات تشترك في NAS. لا يثبت هذا أن كل استعمال يومي يتأثر أو أن المصادقة متوقفة. لكنه يمنع قبول التعايش والمحاسبة الشاملين.

يلزم إصلاح مستقل مدروس يميز إعادة تشغيل NAS الحقيقية من أحداث الخدمة، ويصالح الجلسات قبل الإغلاق النهائي، مع اختبار Accounting-On/Off وإعادة التشغيل وStop المتأخر وتعدد الخدمات. **لا توصية بتعطيل On/Off عشوائيًا أو اختلاق Stop أو تعديل إنتاج الآن**. لم تُطبق رقعة Core أو يُوسّع نطاق صورة Web.

هذا يؤكد الحالة التي كانت غير محسومة في [قبول 2.7.0 السابق](ACCEPTANCE_270_POINTS_123_20261030.md). نجاح Stop النهائي أثناء التنظيف لا يلغي دليل الإغلاق المبكر المحفوظ.
