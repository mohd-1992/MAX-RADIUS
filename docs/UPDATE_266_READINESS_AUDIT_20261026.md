# مراجعة جاهزية التحديث الهوائي 2.6.6 — 26 أكتوبر 2026

## النتيجة والنطاق

مراجعة مصدر واختبارات معزولة بطلب الإنسان، دون تعديل محرك أو لوحة أو قاعدة أعمال، ودون بناء/رفع صور أو تحديث عميل أو دومين أو نشر بيان. لا اتصال بخادم control أو جرد لتركيبات العملاء؛ استنتاجات الحالة الحية تظل خارج هذا التقرير.

المصدر التشغيلي للنظام هو checkout الحالي `max_radius_local`. مصدر مركز الإصدارات الخادمي هو `max_saas_panel_v2_local/backend/release_center.py`، وواجهته `web/update-center.js`. المشروع `max_saas_panel_v2_preview` واجهة مرجعية تضم بيانات توضيحية؛ ليس منفذ تحديث يعتمد للإطلاق. لم تستورد تطبيقات التشغيل لاستخراج فهرس أو تفحص مفاتيح أو اعتماد إنتاجي.

الحكم: أساس قناة التحديث ومحرك Web/Core موجود. إصدار 2.6.6 النهائي غير جاهز للإتاحة العامة؛ يحتاج استكمال التغليف، حسم ترحيل المخطط وترتيبه، واعتماد ترقية/رجوع للصورة النهائية في النموذجين.

## ما يعمل في التصميم الحالي

- القناة تتحقق من توقيع البيان وعرض مؤقت مرتبط بالنسخة والجمهور وبصمة البيان، ومن صور Registry ثابتة. الجمهور عام أو دومين أو نسخة محلية محددة.
- اللوحة تصفي الإعلان بحسب رقم النسخة الأدنى وقدرات القارئ. `migration=explicit` يتطلب قدرة `migration`؛ قارئ MAX الحالي يعلن Web/Core والجمهور الموقع فقط ويرفض الترحيل الصريح. هذا رفض مقصود وليس عطلًا.
- التطبيق يمر عبر منفذ مستقل عن Web، بملكية مشروع وخدمات مثبتة، ونسخة إلزامية، وتحقيق توقيع الناشر والترخيص والـlease، وحفظ journal وCompose وصور الرجوع.
- المحرك الحالي يعيد فحص Web القديمة بعد الرجوع؛ وصف SYSTEM_UPDATES التاريخي بأن الرجوع لا يعيد فحصها لا يصف executor الحالي. لا يعيد DB قديمة.
- لا تحديث لصورة DB أو الأنفاق أو الخدمات المشتركة ضمن هذا العقد، ولا تثبيت صامت: المدير يبدأ التحديث.

## موانع اعتماد 2.6.6 والتعديلات المطلوبة

### 1. اكتمال حزمة البناء — لازم قبل البناء النهائي

`database/schema_healer.py` يستدعي `database.traffic_history_schema`، لكن قائمة COPY الانتقائية في Dockerfile لا تضم الملف. المصدر المربوط في 5122 يخفي هذا النقص عن اختبار الصورة. يلزم تضمينه ومراجعة إغلاق اعتماديات كل الملفات الجديدة، ثم اختبار runtime الموقع دون source mounts، ومطابقة بيان المصدر المجمد والصورة والقوالب والأصول. ليست المشكلة في نصوص المعاينة: شريط التطوير وحالة الترخيص المصطنعة من مشغل خاص خارج البناء؛ تظل مراجعة غيابهما شرط قبول.

### 2. ترحيل مضبوط قبل Core — لازم قبل الإتاحة

`system_update_executor.run_job` يوقف المكونين ثم يبدأ Core ويتحقق منه قبل بدء Web. تهيئة المخطط موجودة في `database.db.init_database` عند بدء التطبيق. Core الجديد يعتمد على العرض `wisp_mac_radcheck` والدالة `fn_account_mac_allowed` في SQL؛ غيابهما في نسخة أقدم يجعل فتح منافذ RADIUS وحده غير كافٍ لإثبات المصادقة. هذا خطر مؤكد من ترتيب المصدر، ولم تُنفذ ترقية جديدة لإثبات أثره حيًا في هذه المراجعة.

المطلوب عقد ترحيل بإصدار وبصمة وخطوات مسموحة من حزمة موقعة، فحص مسبق للمخطط والحقوق والوقت والمساحة، وقفل وإيصال مراحل قابل للتحقق والاستئناف الآمن. تنفذ الإضافات المتوافقة قبل تشغيل Core الجديد مع ضبط تزامن Web القديمة. لا تنفيذ SQL حر يصل من حقل نص في اللوحة. لا تحويل migration إلى none لتجاوز الرفض؛ إن اختير الاعتماد على تهيئة التطبيق فلابد من ترتيب وفحص صريحين يثبتان اكتمالها وتوافقها قبل Core، وتوثيق ذلك في عقد الإصدار.

### 3. ترقية المنفذ القديم نفسه — لازم عند الحاجة إلى القدرة الجديدة

المتحكم ينشأ من الصورة السابقة ويطلق helper منها؛ `persist_compose` يحدّث مراجع Web/Core ولا يرقّي خدمة update_controller تلقائيًا. لذلك إضافة دعم الترحيل داخل Web 2.6.6 وحدها لن تضيفه إلى منفذ بدأ العملية من الإصدار السابق، ولا إلى المتحكم المستقل القائم.

يلزم فصل نسخة بروتوكول المحرك وقدراته عن رقم التطبيق، وخطة ترقية موثوقة للمنفذ. الخيارات: تحديث تمهيدي متوافق بلا ترحيل يجهز المنفذ فعلًا ويختبر استمراره، أو تجهيز مضيف محدود معتمد للتركيبات القديمة. الإجراء الثاني ليس إتاحة عامة تلقائية. لا تثبيت عام قبل مصفوفة الإصدارات ونماذج Compose المدعومة.

### 4. التحقق من إعدادات Core الفعلية — لازم للتركيبات ذات التجاوزات

مرشح الحاوية يرث mounts الحالية. `docker/freeradius/entrypoint.sh` ينسخ queries.conf من `/etc/freeradius-custom` إن وجد؛ صورة جديدة قد تعمل باستعلامات قديمة مربوطة. يلزم جرد محدود لبصمات الإعدادات الفعلية ورفض التجاوز غير المعتمد أو ترحيله صراحة، ومطابقة اعتماديات SQL قبل القبول. لا الكتابة فوق تخصيص مجهول تلقائيًا.

### 5. قبول وظيفي وحدود النجاح — لازم للإطلاق

فحص Core الحالي يبحث منافذ UDP 1812/1813، وفحص Web يتحقق من التوقيع والنسخة والترخيص والـlease وعدم انخفاض عينة آخر 300 صف محاسبة. لا يثبت ذلك قبول مصادقة جديدة ولا وصول Start/Interim/Stop، ولا يشمل كل التاريخ أو المبيعات والعقود.

يلزم فحص الجداول والعروض والدوال والمخطط المتوقع وإيصال الترحيل، وفحص RADIUS/SQL الحقيقي في مختبر معزول، ومقارنات بيانات الأعمال. في الإنتاج تميز النتيجة «نجاح التثبيت والتحقق التقني» عن «رصد مصادقة ومحاسبة طبيعية بعده»؛ غياب الحركة ليس فشلًا. لا مصادقة اختبارية أو فصل للمشتركين دون تفويض مستقل.

### 6. رجوع يحفظ سياسة الماكات والبيانات الجديدة — لازم للإطلاق

الرجوع الحالي يعيد الصور السابقة ويبقي DB الحالية ويتحقق من التشغيل وعينة المحاسبة. لا يثبت أن Core السابق يحترم قائمة الماكات الجديدة؛ صورة قديمة قد تفتح المنافذ مع اختلاف سياسة المصادقة. يلزم زوج رجوع متوافق مختبر بعد وصول محاسبة ومبيعات وتغييرات MAC جديدة. توثّق الإضافات التي تبقى بالمخطط؛ لا DROP عكسي أو DB restore يمس البيانات الجديدة. انقطاع العامل بعد بدء التبديل يذهب للاسترداد، ولا يعد المحرك وعدًا بتعافٍ ذاتي كامل من إعادة تشغيل المضيف؛ يلزم اختبار ذلك وتحديد إجراء الاسترداد.

## تعديلات اللوحة والقناة

- توسيع البيان الموقع: معرف وبصمة خطة الترحيل، نسخة بروتوكول المنفذ المطلوبة، نطاق نسخ التطبيق والمخطط المدعومة، منصة الصورة، وبصمات/توافق زوج الرجوع. حقول migration/rollback الحالية وصفية وليست خطة تنفيذ.
- عرض سبب عدم الأهلية بوضوح: منفذ قديم، مخطط غير مدعوم، تجاوز إعدادات، منصة غير مدعومة، بدل الاكتفاء برسالة «لا يوجد إصدار متوافق». لا كشف لهويات جمهور آخر.
- الإبقاء على فصل المسودة والإتاحة والتنزيل والتثبيت والتحقق الوظيفي. لوحة المركز الحالية لا تسجل إقرار تثبيت عام لكل النسخ؛ سجل update_events هو إنشاء/نشر/سحب، وليس إثبات وصول وتنفيذ. إن أضيف الإقرار فليكن موقعًا ومحدود البيانات ومرتبطًا بالإصدار وهوية النسخة دون حسابات أو SQL خام.
- نشر الصور حاليًا يعتمد `artifacts_verified=True` من المشغل؛ يسجل المصدر صراحة operator-confirmed-not-registry-probed. يوصى بإرفاق بيان قبول آلي موقع/متحقق من مسار البناء قبل السماح بالإتاحة. ليس مطلوبًا منح لوحة control وصول Docker أو Registry؛ يبقى التحقق في جهة بناء معزولة وترسل إثباتاته.
- سحب الإتاحة لا يلغي عاملًا بدأ التثبيت ولا يعيد نسخة ثبتته. يحافظ التقرير والواجهة على هذا المعنى. الإتاحة الأولى موجهة لمجموعة قبول محددة، والعامة لاحقة.

## ما لا يلزم تغييره

لا استبدال صورة MariaDB بسبب إضافة مخطط، ولا تحديث L2TP/Autoheal أو قواعد الترخيص أو المفاتيح الأصلية. لا توسيع محرك التحديث إلى تنفيذ أوامر عامة. لا إعادة كتابة نظام التوقيع أو الجمهور القائمين من الصفر. تحسين Registry/إقرارات الأسطول منفصل عن مانع الترحيل، ولا يصبح بديلًا لقبول الصورة النهائي.

## ترتيب التنفيذ المقترح

1. تثبيت مصدر الإصدار وتصحيح حزمة الملفات ومصفوفة نسخ التطبيق/المخطط/المحرك المدعومة.
2. تصميم عقد ترحيل/رجوع محدود وخطة تجهيز المحرك القديم، ثم اختباره بعزل كامل.
3. تحديث تحقق المحرك وبيان القناة وواجهة الأهلية مع اختبارات التوقيع والتكرار وانقطاع العامل.
4. بناء الصورة النهائية محليًا بتفويض لاحق، ثم قبول تثبيت جديد وترقية دومين وترقية محلية ورجوع بعد محاسبة جديدة، دون bind mounts للمصدر. تتضمن الحالات مخططًا ناقصًا وملف Core متجاوزًا ونسخة احتياطية فاشلة وانقطاعًا بين المراحل وإعادة تشغيل المضيف.
5. رفع وإتاحة محدودة فقط بتفويض لاحق. هذه المراجعة لا تمنح ذلك التفويض.

## تحقق هذه المراجعة وحدوده

## استكمال الفحوص بطلب الإنسان — الجولة الثانية

هذه الجولة لا تعدل المنتج. لم تبن صورًا أو ترفع شيئًا أو تتصل بقناة العملاء أو بياناتهم. ملفات مجسات القبول الخاصة خارج Git، والمخازن المستخدمة مؤقتة اصطناعية مع حجب الشبكة وsubprocess في اختبار اللوحة. Docker المستخدم فقط exec داخل runtime التطوير الموجود لتشغيل اختبارات Fake المعزولة، لا إنشاء أو تبديل خدمات فعلية.

### النتائج الجديدة المثبتة

1. **نجاح العقد الفعلي بين مصدر اللوحة وقارئ MAX:** سبع مجسات تربط إخراج release_center الموقع مباشرة إلى verify_response. نجح Web/Core للدومين والمحلي وWeb فقط للعامة، وترشيح الترحيل الصريح عن القدرات القديمة، ورفضه في المحرك حتى لو أعلن القارئ قدرة migration دون تنفيذها، ومنع إعادة عرض نفس رقم الإصدار.
2. **اختلاف قبول مرجع الصورة بين الطرفين:** أثبتت مجسة ضمن المجموعة أن اللوحة تقبل نشر مرجع Registry ثابت من مستودع آخر، بينما قارئ MAX يرفضه. لوحة المركز تتحقق من صيغة digest العامة ولا تربط مستودع الصورة بدور web/core؛ القارئ يقيد كل دور بمستودعه المحدد. هذا رفض آمن عند العميل، لكنه قد يحجب عمليًا إصدارًا صالحًا أقدم حين تختار اللوحة أعلى إعلان غير قابل للتثبيت. **التعديل اللازم:** توحيد allowlist ومطابقة دور الصورة في validate قبل حفظ المسودة، وفحص ذلك في الطرفين. لا توسيع قبول العميل ليتبع أي مستودع.
3. **ست محاكاة لزوج المكونات:** نجاح Web/Core، فشل Core، فشل Web بعد إنشاء Core، فشل فحص الرجوع، وضياع رد إنشاء Core ثم Web. رجوع الحاويتين تحقق في النموذج، ولا إنشاء ثانٍ بعد الرد المفقود؛ الفشل في إثبات الرجوع انتهى recovery_required. أكدت المحاكاة أيضًا بدء Core قبل Web. هذه محاكاة state machine لا اختبار RADIUS أو DDL حقيقي.
4. **94 حالة انحدار محرك/تجهيز:** مجموع control_update_consumer وupdate_retry_265 وnew_domain_update_bootstrap وold_panel_control_updates وtargeted_release_plan نجح على Linux؛ 92 حالة منفذة وحالتان متجاوزتان. المجموع الجديد مع المجسات 105 فحوص منفذة ناجحة، وحالتان متجاوزتان؛ 17 حالة مركز الإصدارات من الجولة الأولى مستقلة وليست إعادة جديدة في هذه الجولة.
5. **مطابقة المصدر المرجعي:** من 248 ملفًا في بيان مصدر بناء 2.6.5 السابق لم يفقد أي ملف؛ تغيرت بصمات 50 منها في checkout الحالي. هذا ليس حصرًا لتعديلات هذه الجولة، ولا يشمل الملفات الجديدة التي لم تكن في البيان. فحص AST لاعتماديات database في مصدر التشغيل وجد فجوة COPY واحدة مستعملة: traffic_history_schema.py، بما في ذلك استدعاء schema_healer. يلزم بيان مصدر جديد كامل عند تجميد الإصدار؛ لا إعادة استخدام بيان 2.6.5 مع رقم جديد.

Docker Linux فوق مضيف Windows حالة منفصلة تعتمد القالب والمنفذ المختبرين.

### خريطة اعتماد المخطط وترتيب الترقية

- الماكات: ثلاثة جداول policies/addresses/receipts، عرضا account_mac_usernames وmac_radcheck، ودالة fn_account_mac_allowed، مع نقل قيود الماك القديمة داخل التهيئة. Core يعتمد على العرض والدالة؛ أولويتهما قبل تشغيله. تحقق الربط لا يقتصر على CREATE TABLE.
- مصادر البيع: sale_sources وsale_source_audit وأعمدة النسبة والتدقيق، وbackfill عند بدء Web. المثبت يتضمن إسقاط فهرس unique قديم للتدقيق واستبداله؛ لذلك لا يصح اختزال كل التهيئة إلى CREATE IF NOT EXISTS فقط أو افتراض رجوع ذري لمجموعة DDL.
- الاستهلاك: traffic_history وعرض traffic_history_owned، ومسارات حفظ قبل حذف/تنظيف/أرشفة، وملكية تاريخية. وحدته مفقودة من COPY كما في الجولة الأولى.
- التهيئة العامة تشمل كتالوج الصلاحيات وتثبيت دوال/تريغرات المحاسبة وسياسة أول استخدام ومفتاح بيع التفعيل. يجب تعريف مجموعة الكائنات وبصماتها المسموحة قبل/بعد بدل تشغيل healer العام واعتبار كل أثره معلومًا سلفًا. التهيئة الحالية توقف startup عند فشل مطلوب؛ هذا جيد لكنه ليس إيصال مراحل ترحيل.
- نقل قيود الماك وbackfill البيع قد يكتبان صفوفًا إضافية. لا عودة بقاعدة قديمة، ولا إعادة تشغيل backfill/DDL جزئي أعمى؛ DDL في MariaDB ليس معاملة أعمال واحدة يمكن إلغاؤها بالكامل عند الفشل.

### حدود النسخ والمهل والاسترداد

- فحص النسخة يقرأ أعضاء الأرشيف ويتحقق من وجود SQL غير فارغ ويحفظ SHA256؛ لا يستعيدها في قاعدة معزولة ولا يثبت اكتمال كل جدول. المطلوب قبول استعادة مستقل في المختبر للصورة النهائية.
- prepare يمنح استدعاء النسخ 300 ثانية، وسحب كل صورة 600 ثانية؛ محرك dump نفسه قد يسمح حتى ساعة. انقضاء انتظار Docker exec لا يثبت توقف النسخ داخله. يلزم تمييز مهمة نسخ ما زالت جارية من فشلها المؤكد قبل السماح بمحاولة جديدة، وتوحيد ميزانيات الوقت بدل افتراض انتهاء العمل بانتهاء الرد.
- لا يوجد فحص صريح للمساحة الحرة في executor/controller قبل نسخة SQL المؤقتة والأرشيف وسحب الصور وصور الرجوع. المطلوب فحص مواقع التخزين المعنية وحد أمان وتقدير معلن؛ لا تنظيف تلقائي لنسخ أو صور قد يحتاجها الرجوع.
- قفل المهمة والحالة المحفوظة يمنعان تكرار التبديل، وتجديد العرض بعد النسخ/السحب موجود بالفعل؛ لا حاجة لإضافة إعادة جلب مكررة. سحب الإتاحة قبل التبديل يوقف العامل في هذا المسار. السحب بعد بدء التبديل لا يعني إلغاءً ذريًا.
- استعادة التشغيل بعد انقطاع العامل/المضيف ليست وعدًا غير مشروط. الحالات غير المؤكدة قد تنتهي recovery_required وتحتاج إجراء استرداد مضبوطًا. تقبل هذه النتيجة الصريحة بدل نجاح زائف؛ يلزم اختبار عطل فعلي للمضيف لاحقًا.

### ترتيب التعديلات النهائي بعد الاستكمال

**لازم قبل إتاحة 2.6.6:** تصحيح تغليف الملف، عقد وترتيب ترحيل SQL، تجهيز المنفذ السابق، تطابق مستودعات الصور بين اللوحة والقارئ، فحص إعدادات Core المتجاوزة، وقبول زوج الترقية والرجوع بالصورة الفعلية. فحص المنصة والمساحة والمهل مطلوب ضمن preflight قبل اعتماد التوزيع الواسع.

**تقوية متابعة مستقلة:** بيان قبول بناء آلي وإقرار تثبيت محدود البيانات للوحة، مع الإبقاء على control دون Docker. يمكن استمرار تأكيد المشغّل للصور في إطلاق موجه تحت ضبط يدوي؛ لا يوصف بأنه فحص Registry آلي.

**ما بقي غير مختبر عمدًا:** ترحيل DDL حقيقي للصورة النهائية من كل baseline، صلاحيات DB المحدودة، استعادة النسخة، المحاسبة/المصادقة الجديدة، شبكة بطيئة/قرص ممتلئ فعلي، إعادة تشغيل مضيف، الرجوع بعد سياسة MAC وعمليات أعمال جديدة. هذه تتطلب مختبر قبول صور لاحقًا؛ ليست مبررًا لتجربتها على عميل أو دومين.

## الجولة الثالثة — MariaDB وFreeRADIUS فعليان في مختبر جديد

بطلب الإنسان استكملت اختبارات فعلية محلية. استخدمت شبكة Docker داخلية جديدة دون منافذ مضيف، وقاعدة MariaDB جديدة ببيانات مصطنعة في tmpfs، وحاويات بعلامة max.audit فريدة. لم تتصل بعميل أو دومين أو قناة أو Registry. لم تبن صورة جديدة أو تصل إلى Docker Hub. نُفذت تهيئة المصدر داخل runtime موجود؛ هذا ليس اختبار صورة 2.6.6 النهائية المجمعة.

### الصور والحدود

- Web baseline مجمع 2.6.5: `sha256:8c6f40ebc228b6bb3b91b0792ff9b65b071407368b01bcd289f6db127b583a86`.
- Core الجديد المختبر: `sha256:a691a09bc91a…`، والقديم للرجوع: `sha256:7bf2baa71525…` (البصمتان الكاملتان في تقارير الإصدار السابقة).
- تشغيل المصدر الحالي في runtime `eceab63004be…`، لا build جديد ولا توقيع مرشح. الترخيص المستخدم lease SQL اصطناعية معلنة، لا شهادة ترخيص ناشر صحيحة، ولا راوتر MikroTik. حزم UDP أرسلها radclient إلى FreeRADIUS الفعلي داخل الحاوية.
- الأدلة الخاصة: `PRIVATE/sales-history-266-20261025-r1/lab/acceptance-c235998e0f/RESULTS.private.json` والأرشيف وسجلات الحزم المصطنعة المجاورة. لا حسابات عميل أو أسرار إنتاج في التقرير.

### ما نجح فعليًا

1. إنشاء قاعدة بواسطة init_database من بناء 2.6.5 السابق، ثم ترقية المخطط بواسطة المصدر الحالي. دارت التهيئة مرتين وحفظت سجلًا اصطناعيًا بعدادات تتجاوز 4GiB دون تغيير أو تكرار.
2. إنشاء أرشيف بمحرك backup_service الفعلي دون إشعارات، ثم تعديل عداد اصطناعي واستعادة database_dump.sql باستخدام native_mysql_restore وإعادة التهيئة؛ عادت القيم الأصلية. هذا يثبت SQL dump/restore في المختبر، ولا يختبر جميع hooks الخاصة بعملية restore_backup الكاملة.
3. قارئ database المجمّع القديم قرأ السجل نفسه بعد الترقية. لا يعني ذلك قبول بدء Web القديمة أو سياستها بالكامل.
4. بعد التهيئة: Access-Accept للماك المسموح وAccess-Reject لماك غير مسموح. وصلت Start وInterim وStop بردود Accounting-Response، وتحقق صف SQL واحد بمجموعي 4,294,967,419 و8,589,934,647 بايت وإغلاق Stop مثبت. الرصيد الاصطناعي بقي 17.25؛ لم تنفذ شحن/تجديد/شراء.
5. توقفت Core المختبرية ثم أعيد تشغيلها بين Interim وStop؛ نجحت مصادقة لاحقة وحفظ Stop نفس الجلسة والعدادات. لا توجد حزمة أرسلت أثناء فجوة التوقف في هذه الحالة، فلا تثبت تعويض الحزم المفقودة خلالها.

### مانعان مثبتان بالاختبار، وليس مجرد احتمال من المصدر

**بدء Core قبل المخطط:** شُغلت Core الجديدة على قاعدة 2.6.5 الأصلية التي لا تحتوي wisp_mac_radcheck. فتحت منفذ المصادقة، لكن طلب probe المحلي أعاد Access-Reject. بعد ترقية المخطط نجحت طلبات القبول المذكورة. لذلك لا يجوز اعتماد فحص الاستماع على UDP بديلًا عن جاهزية SQL، ويلزم إكمال المخطط قبل Core الجديدة.

**الرجوع إلى زوج 2.6.5 يغيّر إنفاذ قائمة الماكات:** بعد حفظ جلسة جديدة، شغلت تهيئة Web القديمة على القاعدة الحالية ثم Core القديمة، مع تجديد lease SQL الاصطناعية للمختبر. بقي السجل والرصيد، ونجحت مصادقة الماك المسموح، لكن **الماك غير المسموح قُبل أيضًا**. الاختبار رصد النتيجة السلبية ولم يفرض قبولها كنجاح. تهيئة الصورة القديمة تعيد تعريف دوال من إصدارها وCore القديمة لا تستخدم مسار القائمة الجديد نفسه؛ الرجوع يحفظ البيانات لكنه لا يثبت حفظ سياسة المصادقة. يلزم زوج رجوع متوافق أو مسار ترقية يحمي تعريفات السياسة الحديثة، وقبول وظيفي للرجوع قبل النشر. لا استنتاج عن سلوك أي عميل حي من هذا المختبر.

### أثر التحديث على المصادقة والمحاسبة

المحرك يوقف Web/Core القديمة ويبدأ البديل؛ توجد فجوة استقبال RADIUS عند تبديل Core. إيقاف RADIUS وحده لا ينفذ CoA ولا يفصل جلسات الراوتر عمدًا، لكنه لا يضمن استمرار كل جلسة في كل إعداد NAS. طلبات تسجيل دخول جديدة أثناء الفجوة قد تتأخر أو تفشل بحسب retry/timeouts في الراوتر. محاسبة Interim اللاحقة تراكمية وقد تعوض عدادات وسيطة، لكن لا ضمان لتعويض Start/Stop مفقودة أو تجاهل ازدواجها دون فحص NAS فعلي. بقاء SQL ثابتًا وإثبات رد Accounting بعد التشغيل ليس قبول «دون انقطاع».

المطلوب قبل النشر: نافذة تبديل مقاسة، اختبار NAS معزول فعلي وإعادة إرسال/تأخير حزم وفشل بين المراحل، وتحقق من مطابقة الجلسات والعدادات قبل/بعد، دون استعمال disconnect أو DBrestore كحل عام.

### أثر الحاويات المتوقفة

خمس حالات اختيار هوية إضافية: حاويات exited وcreated وdead بنفس labels لم تدخل اختيار الخدمات؛ خدمتا Core عاملتان متطابقتان أو غياب Core عاملة رُفضتا. system_update_executor.owned_snapshot وrenewal_settlement_service الحاليان يشترطان running والملكية، فيعزلان حاويات الرجوع المتوقفة المعتادة.

التوقف وحده ليس عطلًا ولا داعيًا للحذف. قد تؤثر الحاوية المتوقفة إذا حجزت الاسم المستهدف، أو عادت بسياسة restart لتخلق نسختين عاملتين، أو استهلكت صورها/طبقتها مساحة لازمة، أو كان المنفذ القديم يحمل اختيار هوية سابقًا غير مصحح. وسم المشروع وحده لا يكفي؛ يجب فحص الأسماء والسياسة والشبكات والمساحة والبصمات. لا تنظيف شامل ولا compose up عام قد يحذف أو يعيد تشغيل حاويات خارج الهدف. المحرك يحفظ القديمة ويغير restart إلى no ضمن جولته.

### ما لم يكتمل بعد ولماذا

لم تبن الصورة النهائية لأن مصدر الحزمة كما هو يفتقد ملف schema مطلوبًا، ولم يُعدّل الكود ضمن مهمة الاختبارات. لا قبول لترقية هوائية 2.6.6 كاملة ما دام عقد الترحيل والمنفذ المتوافق غير منفذين. لم تُختبر استعادة hooks الكاملة، راوتر فعلي، انقطاع كهرباء/إعادة تشغيل المضيف، امتلاء قرص أو شبكة بطيئة فعلية، كل baseline وصلاحياته، أو ترخيص ناشر صحيح بعد تبديل كامل. هذه تظل شروط قبول لاحقة بعد إصلاح الموانع، ولا يعوضها نجاح المصدر أو SQL/RADIUS في هذه الجولة.

تعثرت محاولات fixture الأولى في حجز subnet تلقائي ثم مسار استيراد baseline وحقل package_id المطلوب في بيانات التجربة؛ أصلحت أدوات المختبر فقط وأُنشئت جولات جديدة دون إعادة جولة أعمال قائمة. جميع خدمات هذه الجولات أوقفت، ثم أزيلت الحاويات المتوقفة والشبكات التي تطابق علامات ملكيتها فقط؛ ملفات الأدلة بقيت ولم تحذف صور أو حاويات سابقة خارج نطاق الجولة.
