## العميل: ما ثبت وما ينقص

ثبت HOST-LOCK وبصمة Docker وSSH. تطابقت هويات وصور وحالات التشغيل وأوقات البدء وإعادة التشغيل لجميع الحاويات العشرين قبل القراءة وبعدها. الحراس والمساعدون المتوقفون يخصون جولات مكتملة؛ لا يستأنفون لتجهيز هذا الإصدار.

نجح اختبار حسابي باستخدام `candidate_spec` من الصورة العاملة، دون إنشاء حاوية أو Docker mutation. حافظ التعريف المقترح على mounts وentrypoint وcommand وenv عدا HOSTNAME المولد، وحدود RAM، وعنوان Web172.18.0.14 وaliases. هذا يثبت إمكانية بناء التعريف، **ولا يثبت سلامة تشغيله والرجوع به عمليًا**. يجب إبقاء Core172.18.0.3 وتوجيه RADIUS كما هما.

ملفات native-kit وcontrol-new وoverride لجولة6نوفمبر تبعيات تشغيل حية. يلزم حفظها في تعريف التشغيل الدائم والرجوع، ولا تحذف كمخلفات نسخة قديمة.

نجح طلب مفتاح القناة باستخدام User-Agent الفعلي للمحدّث وطابقت بصمة المفتاح القناة المعتمدة. طلب urllib الافتراضي أعاد403، لكن الطلب الفعلي أعاد200؛ لم يثبت مانع اتصال للمحدّث. أعادت قراءة manifest الصورة2.7.1 من DockerHub200 وبصمة مطابقة، دون تنزيل طبقات.

المتاح وقت الجرد نحو24.79GiB قرص و4.70GiB RAM، وswap غير مستخدم. أحدث نسخة محلية43.24MiB، مكتوبة7نوفمبر15:01:57 بتوقيت عدن. لم تنشأ نسخة أو تنقل أو تفك أو تجرب استعادة في هذه المراجعة؛ وجود الملف وحده لا يثبت قابلية الاستعادة.

قبل الإرسال يحتاج العميل:

1. هوية Local مستقلة مرتبطة بالنسخة، وثقة مثبتة وقناة محمية وختم مخطط موثق. هوية Local الموجودة بالقناة تخص مختبر10.10.10.8 ولا تستخدم للعميل.
2. منفذ تحديث محدود، مع ربط مقبسه بالويب وحفظ ملفات التشغيل الحالية. تسجيل الاستهداف وحده لا يشغّل منفذًا غير موجود.
3. اختبار التهيئة والنسخ والتحويل والرجوع على نسخة معزولة تماثل العميل، ثم خطة قبول تحافظ على الترخيص والمصادقة والمحاسبة الطبيعية.

## m.max-r.cc: مسار خاص بلوحته

فُحصت خدمة الاستضافة الفعلية بعملية `inventory` للقراءة عبر agent.sock، دون استيراد تطبيق اللوحة أو إنشاء worker. المنظومة ready وخدمتها تعمل، لكن قائمة الانتقالات المقبولة فارغة، ولا يوجد قارئ أو تسجيل متحكم ناشر خاص بها.

الكتالوج قديم بالنسبة للصور العاملة: مرجعه2.7.0 يتطلب Core10cc، والمستأجر يعمل بـCore6e71. كود الاستضافة يرفض انتقالًا يغير Core أو لم يُقبل توافق الرجوع له. لا يكفي نسخ بيان max1 أو تغيير اسم الدومين فيه.

المطلوب قبل الإرسال:

1. اعتماد2.7.1 في كتالوج هذه اللوحة، بـWeb ef615475 و**نفس Core الحالية6e71**؛ دون تبديل Core أو DB أو خدمات النفق.
2. اختبار توافق الرجوع إلى Web513d ثم تسجيل قبوله، مع حفظ binding وnative-kit والترخيص والتخزين والتوقيت والبيئة. لا يوضع `rollback_compatible=true` لمجرد تجاوز رفض الكتالوج.
3. تسجيل قارئ مملوك لهذا المستأجر، والتحقق من عرض البيان وتوقيعه واستهدافه من لوحته؛ دون إعلان عام أو هوية من اللوحة القديمة.
4. النسخ يخص schema وتخزين m وحده. محرك max-db-a تديره المنصة وخارج حاويتي المستأجر؛ لا يوقف أو يحدث ضمن تحديث Web. كان m المستأجر الجاهز الوحيد في PoolA وقت القراءة، ولا يفترض ذلك دائمًا.

هذا المسار لا يستخدم ملكية مشروع Compose ذي Web/Core/DB كما في max1.max-net.net. يلزم قبول مسار الاستضافة الأصلي؛ لا إضافة ملصقات أو توسيع socket لتجاوز الرفض.

## شرط أمان للمنظومات النشطة

في مصدر محرك القناة3، قد ينتظر `wait_ready` مدة150ثانية لجهوزية Web، بينما lease التي تنشرها Web للراديوس مدتها90ثانية. **هذا خطر فشل مشروط مستنتج من الكود، وليس انقطاعًا مرصودًا.** عند تعذر الإقلاع أو تجديد lease قد ينتهي هامش الترخيص قبل قرار الرجوع، وقد تضيف عملية probe وقتًا فوق مهلة الحلقة.

وفي مسار الاستضافة الأصلي، يعتمد `verify_web` على HTTP والترخيص والنسخة. نجاحه وحده لا يثبت توقيع runtime وربط Core وlease وتقدم المحاسبة. يلزم قبول هذه المؤشرات قبل إقرار الانتقال لمنظومة نشطة.

التوصية: اختبار الحارس والرجوع بمهلة مبنية على **الوقت المتبقي في lease وهامش الرجوع**، مع حالات تعثر الإقلاع وفشل الترخيص وفقد رد العامل. لا تطال مدة الترخيص أو تعطل حمايته لحل المشكلة. بعد التبديل أو الرجوع يفحص التوقيع والهوية والكور المقصودة والتوقيت والترخيص والمصادقة الطبيعية وUID وتقدم العدادات. لا استعادة DB تاريخية للرجوع عن Web، ولا إعادة معاملة مالية.

Web وحدها خدمة التطبيق المستهدفة بالصورة الجديدة؛ تهيئة المحدّث وحارسه عمل مستقل ولا تعني تحديث Core أو صورة MariaDB. توقف واجهة Web أثناء التبديل متوقع، ولا يوجد إثبات انقطاع صفري أو سلامة كل NAS من الفحوص الحالية.
