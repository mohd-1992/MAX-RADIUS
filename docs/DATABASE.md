# قاعدة البيانات والترحيلات

إصلاح أقفال تفعيل الكروت المختبر في 16 أكتوبر يفصل تحديد اسم المستخدم/PIN عن قفل الكرت بالمفتاح الأساسي، ويقرأ الحزمة والباقة دون قفل ربط واسع. يشمل تريغر المحاسبة والتفعيل اليدوي، مع فهرس PIN متكرر آمن وانتظار metadata محدود عند إنشائه. الحالة مختبرية فقط؛ [التقرير والحدود](archive/2026-10-16-voucher-activation-lock.md).

مصدر الاتصال: [database/db.py](../database/db.py). الاتصال يلتزم بالخلفية المحددة ويمنع التحول التلقائي من MySQL إلى SQLite عند تعطل DB. استخدم معاملات placeholders و`db_session`/أدوات المعاملات الموجودة بدل تركيب قيم SQL.

مصادر إنشاء المخطط: `database/schema_mysql.sql` و`init_db.sql`، وتعريفات الترقية/التريغرات في `database/schema_healer.py` والوحدات المتخصصة. `database/full_db.sql` dump تاريخي مستبعد من Git؛ لا تعدله كبديل لترحيل ولا تغير أعمدته مع INSERT positional قديم.

عند تعديل المخطط: حدّث كل مسار إنشاء يستخدم التعريف، وثبّت ترحيلًا قابلًا لإعادة التشغيل ويحافظ على البيانات. تحقق من أنواع القيم والفهارس والتريغرات والقراءات والكتابات في الخدمات. احتفظ بنسخة قبل الترحيل الحي ضمن نطاق التفويض. DDL في MySQL قد يثبت ضمنيًا؛ لا تفترض أن rollback يعكس ALTER.

اختبر التريغر من اتصال مستقل تحت التزامن؛ الاختبار الوظيفي التسلسلي لا يكشف gap locks. تشغيل ترحيل البيع مجددًا يجب ألا يغيّر المبيعات أو ينقل مفتاح التفعيل الموجود. [قرار البيع](decisions/002-first-activation-sale.md).

الاستيراد: حدد نوع المحرك وخيار التفاصيل، ثم قارن المصدر بالنتيجة باستخدام أعداد وIDs وحالات وأرصدة وجلسات. راجع `@max_radius_import` وآلية snapshots في المحرك المعني قبل إدخال تاريخ محاسبة قد يشغل تريغرات التفعيل.

امتداد بيانات صلاحيات المدراء: `database/permission_catalog.py`، يستدعيه bootstrap MySQL بعد التهيئة. المعاملة تضيف إلى wisp_permissions وwisp_role_permissions فقط؛ لا تغير المخطط أو تعيد منح خيارات موجودة. المصدر الوصفي `core/permission_catalog.py`؛ راجع MANAGERS لتبعيات الصلاحيات وحدود ملكية الموزع. لا تستدعِ init_database كله لتحديث هذا الكتالوج في نسخة تعمل؛ استخدم المثبت المحدد ضمن نشر مصرح به.

أداة المقارنة المحلية تقبل JSON مخطط فقط بصيغة `{"tables":{"table":{"columns":{},"indexes":{}}}}`؛ لا ترفع بيانات العملاء أو credentials إلى هذه الملفات.

## إيصالات الإصدار السريع

`database/quick_card_schema.py:install_quick_card_schema` يضيف جدول wisp_quick_card_issues، بمفتاح فريد (actor_id,request_key) وفهرس الملكية. يستدعيه bootstrap MySQL بعد تركيب RBAC؛ النشر الذي يتجاوز bootstrap يشغله صراحة قبل الويب. CREATE IF NOT EXISTS متكرر آمن، وDDL مستقل قبل أي إصدار مالي. لا ترحيل لأرصدة أو تعديل لصفوف قديمة. لا FK للحزمة حتى يبقى إيصال العملية بعد حذف كروتها؛ IDs الموجودة رتيبة ولا يعاد استخدامها. إعادة المصنع يمسح هذا السجل مع الكروت؛ إعداد صيغة الإصدار العام يبقى ضمن إعدادات النظام كالمعتاد.


## مهام User Manager
تحديث التنفيذ المحلي 17 أكتوبر: سجلان إضافيان `wisp_userman_import_batches` و`wisp_userman_import_journal` يحفظان إيصال الدفعة وصور قبل/بعد داخل معاملة البيانات. الإلغاء يعكس فقط الأثر الذي بقي مطابقًا ولم تطرأ عليه محاسبة/قبول/بيع/حجز أو تغير عقد/حد دورة؛ التعارض يحفظ الحالة للمراجعة ويظهر cancelled_partial. لا يحذف محاسبة NAS الفعلية أو baseline أو مالية. التراجع ذري لكل حساب وقابل للاستئناف دون إعادة الدفعات أو استعمال المعرفات المحذوفة.

المثبت `database/userman_import_schema.py` ينشئ الجداول وفهرس username للحجوزات قبل معاملة البيانات، بمهلة metadata ثانيتين مع إعادة المهلة الأصلية. bootstrap وDockerfile يشملانه. المعاملات تستخدم REPEATABLE READ وأقفالًا محدودة؛ لا تعطيل للمفاتيح الأجنبية. ما يلي وصف تاريخي للآلية قبل إضافة التراجع المشروط؛ عبارة بقاء الدفعات السابقة أدناه لم تعد سلوك الإلغاء الجديد.
المصدر الكامل والمعاينة وسجل التقدم في storage/userman-jobs بملفات600ومجلدات700، خارج صورة Docker وGit وstatic. اعتماد الراوتر يبقى في ذاكرة العامل فقط. صاحب المهمة وصلاحية الاستيراد شرط لقراءة النتيجة والإلغاء. كل200سجل معاملة منفصلة؛ الإلغاء قبل commit يتراجع عن الدفعة الجارية، والدفعات السابقة محفوظة. خيارات الطلب مرتبطة ببصمة ومرجع يمنع إعادة المحاولة المالية للمصدر نفسه. batch-in-flight يحفظ الغموض عند توقف العامل؛ لا استكمال تلقائي بعد إعادة تشغيل الخدمة. مسار إعادة المصنع يرفض البدء أثناء قفل userman-import، والعامل يرفض الاستيراد أثناء إعادة المصنع. هذه الآلية لا تعيد تصنيف أو تعديل كروت عميل قائمة عند النشر.

## التهيئة دون إعادة إنشاء غير ضرورية

يقارن [schema_objects.py](../database/schema_objects.py) تعريف الدالة أو التريغر كاملًا قبلDDL. يُتجاوز التعريف المطابق؛ اختلاف التوقيع أو الجسم يستلزم تثبيتًا وقراءة تحقق لاحقة. اختلافDEFINER وصيغ عرضMariaDB المكافئة لا يغيّر المقارنة؛ النصوص الحرفية تبقى معتبرة. إذا أظهرMariaDB وجود دالة من bootstrap إداري دون السماح بقراءة تعريفها، فلا تُعتبر متحققة: تثبت النسخة المعتمدة ثم يجب أن تصبح قابلة للقراءة والمطابقة، دون منح صلاحيات إدارية إضافية.

مهلة metadata lock المطلوبة داخل التهيئة وتعريفات الكائنات ثانيتان. يرد التعذر كخطأ؛ لا تُعتبر حالة القفل نجاحًا، ولا تتغير دلالةDDL ذات التثبيت الضمني. تبقى التغييرات الحقيقية بحاجة لنسخة رجوع وتحقق الهدف؛ التهيئة ليست معاملة مالية قابلة للتراجع.

يفحص healer حاجة تعبئة global_seq_id واللقطات قبل تنفيذها، ويحافظ علىNULL المقصود لسياسة أول استخدام، وعلى قواعد إصلاح البيانات القديمة. إعادة التهيئة المطابقة لا تُبطل أو تمددlease سارية. اختلاف قواعد سعة الترخيص يُبطلlease السابقة قبل أولDDL، حتى عند فشل الترحيل؛ لا تُستعاد الصلاحية إلا من المسار المعتاد للتحقق من الترخيص. لا تغيير لتعريفات المحاسبة أو عقود الرصيد.

التثبيت الجديد يتبع Compose: يشغّل MariaDB `database/schema_mysql.sql` أولًا، ثم تبدأ تهيئة التطبيق. نداء `init_database` وحده على قاعدة خالية ليس بديلًا لاختبار المثبت كاملًا. فحوص16أكتوبر في [TESTING](TESTING.md) والتقرير الخاص المشار إليه في [CURRENT_STATE](CURRENT_STATE.md).
